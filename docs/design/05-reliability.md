# 设计 05 · 可靠性

> 依据：FR-34~38, CR-6/10/11, INV-45/46/51 · [D21](../architecture/decisions.md#d21-可靠性分层三类存储的差异化投入)

---

## 1. 存储分层

| 存储 | 丢失后果 | 写频率 | 高可用价值 | 高可用成本 | 本期决策 |
|---|---|---|---|---|---|
| 会话主快照 | **历史永久丢失，无法继续对话** | ~70/s | 最高 | 低 | 真库 + 同城多可用区主备 + 备份 |
| 账本 | 生成记录 / 计费 / 幂等键丢失 | ~70/s | 高 | 低 | 与上同表同事务（D30 起终态同事务） |
| 在途事件缓冲 | 调用方重试该次生成 | **~2 万/s** | 中 | **最高** | 共享中间件（Redis Streams / TDMQ 等）+ 四项缓解 |

**这是 D11 的当代表述**：两侧写频率差约三个数量级，必须分承载。结论未变；在途缓冲已按 D25 落地为共享中间件（§6.1 的选型由「届时」变为「已生效」）。

---

## 2. 故障语义分层

这是本设计对外承诺的核心：

| 故障 | 已完成生成 | 在途生成 | 历史 |
|---|---|---|---|
| 网关进程崩溃 | 不受影响 | **明确失败，可重试** | **完好** |
| 执行端崩溃 | 不受影响 | 新 attempt 重跑 | 完好 |
| 整机 / 可用区故障 | 不受影响（多可用区） | 重跑 | 完好 |
| 滚动发布 | 不受影响 | **无损**（优雅停机） | 完好 |
| 会话快照 / 账本不可用 | 查询失败 | **拒绝新建（503）** | 完好 |

关键点：**在途失败永不牵连历史**。这是分层的直接产物——两者承载不同。

## 3. 在途高可用的结论（D25 已落地共享中间件）

共享中间件**确实**能买到真实可用性，且已按 D25 落地。但价值只集中在两种情形——这一点在当时评估时已确认：

| 崩溃对象 | 进程内内存 | 共享中间件 | 差异真实? |
|---|---|---|---|
| **网关挂、执行端存活** | append 失败，生成被孤立作废 | 执行端改投他节点，**生成不中断** | ✅ |
| 执行端挂 | 新 attempt 重跑 | 同 | ❌ |
| 整机 / 可用区 | 重跑 | 同 | ❌ |
| **滚动发布** | 在途全丢 | 无损 | ✅ |

第 2、3 行无差异的根因：**LLM 生成本身不可中途续跑**（模型 API 性质，非架构缺陷）。按 attempt 栅栏语义，重试必然是新 attempt，旧 attempt 的部分输出必须作废，否则输出交织违反 CR-3。故即使事件一条不丢，调用方读到的也只是「失败前的部分输出 + 失败事件」——**生成不会继续**。

两处真实收益的处置不同：

- **滚动发布**（最高频）：由优雅停机**零成本消除**。发布是计划内动作，可先拒新、等在途完成再退出
- **网关挂、执行端存活**：由共享缓冲消除——执行在独立进程，缓冲在共享载体，网关崩溃不打断在途生成

**非计划崩溃**无法消除：月损失率约 **0.031%**（悲观 0.093%），满足 99.9% 但**几乎无余量**。

## 4. 四项缓解（缺一不可）

### 4.1 优雅停机

```
SIGTERM → accepting = false      # 创建 503；查询与订阅继续
        → 轮询在途归零 / 超时
        → 退出
```

**单项价值最高**：一次不 drain 的发布损失全部在途（10 节点 × 1400 ≈ 1.4 万），相当于 10 次崩溃。

超时后剩余在途由下次启动的孤儿收口置失败——仍是显式失败，不挂起。这是有意取舍：单个超长生成不得无限阻塞发布。

> 若生成时长 P99 > 15 分钟，drain 不再可行，触发三层高可用评估（见 §6）。

### 4.2 失联领取的心跳收口（reap）

执行进程独立后没有「启动期扫自己的孤儿」这一步——崩掉的 agentd 不会再启动。失联 claim 由 gateway 内嵌的 sweep 按心跳超时回收：`in_progress` 且 owner 心跳超 `heartbeat_ttl` 的领取被抬栅栏并置失败。

```sql
UPDATE responses SET attempt = attempt + 1, status = 'failed', …
 WHERE status = 'in_progress'
   AND (owner IS NULL
        OR NOT EXISTS (SELECT 1 FROM agent_heartbeats h
                        WHERE h.agent_id = responses.owner
                          AND $1 - h.last_seen_ms <= $2))
RETURNING response_id, attempt - 1 AS previous_attempt
```

把心跳超时的挂起变为**明确失败**。抬高 attempt 是必需的：否则失联执行端若仍存活，其 append 会被接受。

claim 全局化（D25）后**不再按 node_tag 收口**——在途缓冲共享，任何执行进程可领取任意 queued 生成，孤儿回收同样是全局的。

### 4.2.1 取消传播：执行端主动感知并停止

用户取消必须让执行端**及时停止**，否则 ReAct loop 继续生成、持续计费。`cancel` 因此与 `reap` 一样**抬 attempt fence**（INV-60）：执行端下一次 append 会被 `StaleAttempt` 拒绝（被动），主动取消探测（`CancelProbe`）也观察到同一信号。

被动检测只在执行端恰好 append 事件时触发；阻塞的 **tool call 执行期间没有任何 append**，故 runner 用 `tokio::select!` 把工具调用与 `CancelProbe::cancelled()` 竞速，tool call 中途也能及时终止。

`CancelProbe` 底层是轮询 `ledger.check_attempt`（INV-6），间隔可配（默认 250ms，`cancel_poll_interval`）——轮询贴合独立执行进程（D25）无内存共享的现实，一次轻量账本读的代价可忽略，换来 tool call 最多延迟一个间隔即感知取消。

### 4.3 部分用量入账

中途作废时 token 已消耗，必须记录，否则计费对不上账。

`partial_usage` 按 attempt 键存储，故重复作废累加而非覆盖。回收与取消**在同一语句内**完成状态转换与用量记账，避免两者之间崩溃导致丢账：

```sql
partial_usage = CASE
    WHEN usage = '{}'::jsonb THEN partial_usage
    ELSE jsonb_set(partial_usage, ARRAY[attempt::text], usage, true)
END
```

（PostgreSQL 中 `UPDATE` 的 SET 表达式引用**旧值**，故 `attempt::text` 正是被作废的那个 attempt。）

### 4.4 持久存储不可用时拒写

`store: true` 的创建请求返回 `503`，**绝不降级为静默不存**。

这是四项中最隐蔽的一项：静默不存会让本次请求看起来成功，而故障推迟到**某个无关的后续请求**（链断裂）。那是最难排查的失败模式。

启动时也探活一次：无法存储的节点不应开始接受流量，失败得早比服务 503 更清晰。

## 5. 后台维护合并为单循环

回收失联领取、释放过期事件缓冲、清理过期会话快照**同一 tick（2s）完成**，由能力层的 `ResponsesService`（`start` 启动、`stop` 停止）承担，每节点各跑一份——reap 幂等，冗余循环只竞争不重复收口。三个独立循环意味着三个定时器与三次遗漏机会。

```
tick:
  1. ledger.reap(now, heartbeat_ttl)   → 抬栅栏 + 记部分用量 + 发失败事件 + close
  2. event_log.sweep_expired(now)      → 释放过保留窗口的 response 事件流（TTL）
  3. conversation 冷快照保留策略         → 按配置清理过期会话主快照（D30 新增载体）
```

## 6. 三层高可用（在途共享中间件）已按 D25 落地

在途缓冲已由共享中间件承载（Redis Streams / TDMQ 等，见 §6.1）。当时评估的触发条件是：

| # | 条件 | 判定 |
|---|---|---|
| 1 | 非计划网关崩溃失败率 **> 0.05%/月** | 实测，不接受预判 |
| 2 | 单次生成时长 **P99 > 15 分钟** | drain 预算不再可行 |
| 3 | 合作方明确要求「网关故障对生成无感知」并接受延迟与成本 | 产品需求提出即触发 |

条件 1、2 的输入（`A9` 崩溃频次、`A3` 生成时长）仍须纳入常规监控（OR-4），作为是否进一步优化在途高可用的依据。

### 6.1 选 Redis Streams 而非消息队列

| 维度 | Redis Streams | 消息队列 |
|---|---|---|
| 游标模型 | **按标识范围随机定位**，与 `starting_after=N` 同构 | 消费者游标模型，需额外维护「序号 ↔ 位点」映射 |
| 高基数短命 topic | 一键一流，创建销毁廉价 | 每次生成一个 topic ⇒ **元数据抖动** |
| 追加延迟 | 内存写，亚毫秒 | 三副本持久化，**毫秒级** ⇒ 损害逐字输出体感 |
| 生命周期匹配 | 分钟级短流，`MAXLEN` 天然有界 | 面向长期保留设计，短流是反模式 |

**该决定可逆且已验证**：`ResponseEventLog` 端口形状即抽象层，`mock-server`（验证载体）与接入方的生产存储后端（如 Redis Streams / TDMQ / JetStream）并存——领域层与接入层零改动。

## 7. 灾备

同城多可用区主备 + 定期备份。**不做跨地域**（继承 D8）：复杂度与 99.9% 目标不匹配。

会话主快照容量 ≈ 135 GB（30 天保留，含索引），属常规单实例量级，无需分片。

## 8. 实现期发现的两个真实缺陷

记录在案，因为两者都属于「测试不写就发现不了」的类别：

### 8.1 终态事件被自身栅栏拒绝

`complete` 先调 `ledger.complete`（状态转终态），再 append 终态事件。若该事件带 `attempt`，栅栏校验会因「状态已非 in_progress」而拒绝它——**流永不终止，同步模式必然超时**。

修正：服务端自己发出的信封事件不带 `attempt`。栅栏的作用面是**执行端写入**，而账本已在此前校验过 `expected_attempt`。

### 8.2 夹具 teardown 用 SIGTERM 反而卡住端口

`SIGTERM` 会启动优雅停机。若夹具里留有挂起的在途生成（如 `hang` 输入），drain 会一直等到预算耗尽，端口被占住，下一次运行报出令人困惑的 `503`。

修正：teardown 用 `SIGKILL`（必须确定性），夹具配置另设短 drain 预算（3s）。**只有验证 drain 本身的场景才用 SIGTERM**。
