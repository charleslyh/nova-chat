## D1 容量模型不在架构层锁定

| | |
|---|---|
| **需求** | FR-2.1 容量感知、FR-2.6 容量模型可扩展 |
| **结论** | 不预设容量维度。抽象为「匹配器」，匹配规则以受限 DSL 表达，可不停机替换 |
| **代价** | 引入代码执行入口 ⇒ 派生 SEC-6（沙箱）与 INV-17~INV-20 |

**理由**：容量形态（标量 / 向量 / 附带标签）在需求阶段无法确定，锁定任一形态都会在业务演进时引发核心流程改造。

**成立前提**：由 D3 支付。任意 DSL 谓词**无法下推到索引**，只能「取候选逐条求值」。池 < 1 万时该成本可忽略；若池达 1e7 量级，此决策不成立。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| 锁定单维标量 | 无法表达标签约束与多维容量，业务演进即需改造核心 |
| 锁定多维向量 | 过度设计；且仍无法表达非数值型约束 |

## D2 匹配采用 first-fit + 设备自主拉取

| | |
|---|---|
| **需求** | FR-2.3 无队头阻塞、SR-1 水平扩容 |
| **结论** | 设备主动拉取，扫描候选窗口，**满足即领取**，不追求最优装箱 |
| **代价** | 装箱非最优（范围界定 S2 已接受） |

**理由**：first-fit 使匹配决策**完全本地化**，无需中心组件掌握全局视图。这直接消除了中心调度器及其选主机制。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| best-fit（设备扫窗口选最贴合） | 装箱略优，但需更大候选窗口；当前装箱率目标 70% 无需此优化 |
| 全局最优（中心调度器统一分配） | **需选主**，且成为吞吐瓶颈与单点。装箱收益不足以抵偿复杂度 |

## D3 规模按 DAU 50 万为设计基准

| | |
|---|---|
| **依据** | `parameters.md` §2 锚点、§4 导出量 |
| **结论** | 池 < 1 万、峰值领取 70/s、并发任务 2.1 万、设备 1.05 万；适用区间取 5~14 倍 |

**理由**：DAU 是唯一可观测的业务锚点，其余参数由守恒关系导出（§3）。规模不可预估时，以「适用区间 + 越界阈值」替代精确值。

**关键推论**：此规模使 D1（DSL 逐条求值）与单一强一致判定点均成立。**D3 越界会同时动摇 D1 与 D2。**

## D4 领取不跨区域

| | |
|---|---|
| **需求** | 冲突 X5（CR-1 领取唯一性 × FR-1 多区域低延迟） |
| **结论** | 任务与执行设备按区域绑定，领取判定不跨区域 |

**理由**：唯一性判定必须集中，跨区域领取会在关键路径引入区域间往返延迟（< 200ms）。区域内绑定使 X5 无需仲裁。

> **注意**：这不影响 FR-11（跨区域观测）——**观测是读路径，与领取解耦**。

## D5 防饥饿采用老化 + 定向预留排水

| | |
|---|---|
| **需求** | FR-2.4、`spec.md` §3.2 两类饥饿 |
| **结论** | 排序型饥饿用排序老化；**容量型饥饿用定向预留 + 排水** |
| **代价** | 排水期间容量闲置，装箱率下降（冲突 X2，由装箱率目标 70% 仲裁） |

**理由**：**老化只能解决排序型饥饿。** 容量型饥饿（需求 8 而剩余恒为 4）中任务不可行，排到第一也领不走，必须阻止小任务继续占用容量。

**成立前提**：依赖 D9 的静态执行上界为排水时间提供确定上界。若执行时长无界，则排水时间无界，FR-2.4 不可验收。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| 仅做老化 | **不满足 FR-2.4**，遗留一类永不执行的任务 |
| 全局屏障（停止所有小任务派发） | 影响面过大，吞吐损失远超定向预留 |

## D6 不做抢占

| | |
|---|---|
| **结论** | 高优先级任务不中断已在执行的任务（范围界定 S4） |
| **代价** | 高优先级任务的等待时长受在途任务时长影响 |

**理由**：抢占需检查点与续跑能力，复杂度陡增。当前高优先级等待 P95 < 1 分钟的目标可由优先级排序满足。

> **不做抢占不豁免 FR-2.4**：无饥饿仍须由 D5 保证。

## D8 单域起步

| | |
|---|---|
| **结论** | 单一区域承担任务权威状态，不做容灾切换（范围界定 S6） |
| **代价** | 该区域故障时提交与领取不可用（可用性目标 99.9% 可接受） |

**理由**：D4 已确定领取不跨区域，多域的主要价值（容灾）需要跨域一致性协议与故障转移，复杂度与当前可用性目标不匹配。

> **观测层仍是多区域的**：观测者可就近接入（FR-11），因为读路径无一致性要求。

## D9 不做任务级执行权时限与续期

| | |
|---|---|
| **需求** | FR-18 失联回收、SR-4 长耗时任务、冲突 X14 |
| **结论** | **设备级存活信号**（每设备一个）+ **任务静态执行时长上界**（领取时写定，永不更新） |
| **代价** | 任务卡死的发现延迟至执行上界（4 小时），而非一个续期周期 |

**理由**

| 维度 | 本决策 | 任务级时限 + 续期 |
|------|-------|------------------|
| 需维护的时限对象 | 每设备 1 个 | **每在途任务 1 个** |
| 续期逻辑 | **无** | 需要，且需防误判 |
| 长耗时任务风险 | 低（判定与任务时长无关） | **高**——续期间隔配错、执行线程阻塞均会**误杀正在正常执行的任务**，与 SR-4 直接冲突 |

**关键洞察**：续期机制的失败模式是「破坏正确性」（误杀正常任务），而本决策下自检失败的后果仅为「浪费算力」。**故障模式严重性降级是本决策的主要收益，而非仅是简化。**

**派生约束**

- 自检必须只读（INV-7），否则退化为续期
- 执行上界必须静态（INV-9），否则等价于续期，且排水时间失去上界
- **尝试序号仍必须存在**（INV-5）——它是 CR-4/CR-8 的唯一依据，且本就承担 FR-6 重试计数

**后续引入条件**（满足任一）

- 卡死频率使「等到执行上界」的资源浪费不可接受
- 需区分「设备健康」与「单任务健康」以支撑更细的调度
- 单设备并发任务数升高，使设备级回收的影响面过大

## D10 容量账本由服务端核算

| | |
|---|---|
| **需求** | CR-3 容量不超卖、CR-10 容量账目可信 |
| **结论** | 执行设备只上报**静态总容量**与存活信号；**剩余容量由服务端按在途任务聚合推算** |
| **代价** | 领取时需一次聚合查询（D3 规模下成本可忽略） |

**理由**：若采信设备自报的剩余容量，**设备谎报即可绕过容量约束，FR-2.1 形同虚设**。容量账本必须在服务端，这是 CR-10 的唯一实现路径。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| 设备自报剩余容量 | **不满足 CR-10**；容量约束可被绕过 |
| 设备自报 + 服务端抽查 | 抽查窗口内仍可超卖，且复杂度高于直接核算 |

## D11 领取路径与输出路径分离

| | |
|---|---|
| **依据** | `parameters.md` §4.4 输出数据量推导 |
| **结论** | 任务领取与流式输出**不共用同一承载**：领取为低频强一致，输出为高频可批量 |

**理由（量化）**

| 路径 | 吞吐 | 一致性要求 |
|------|------|-----------|
| 任务领取 | **70/s** | 强一致（CR-1 唯一性判定） |
| 流式输出 | **10 万条/s** | 保序即可（CR-6） |

二者吞吐相差约 **4 个数量级**，一致性要求也不同。用同一承载会导致：要么为满足输出吞吐而牺牲领取的强一致，要么为满足领取的强一致而无法承载输出吞吐。

> **这是本决策集中唯一由量化数据强制得出的架构分层**，而非设计偏好。

## D12 策略切换采用请求级版本快照

| | |
|---|---|
| **需求** | FR-19 不停机调整策略、OR-5 变更可审计可回滚、冲突 X13 |
| **结论** | ① 单次领取全程使用**同一版本**的匹配器（版本快照）；② **允许不同副本短暂持有不同版本**；③ **收紧型变更**须额外采取双版本校验或暂停切换 |
| **代价** | 切换窗口期内（配置传播时长，秒级）不同副本按不同 `rank` 排序，FR-2.2 优先级偏序**短暂降级** |

### 前提修正：切换期不威胁 CR-1 / CR-3

冲突矩阵 X13 最初判断策略切换会威胁 CR-1（不双领）与 CR-3（不超卖）。**该判断不成立**：

| 需求 | 实际保证者 | 与匹配规则的关系 |
|------|-----------|----------------|
| CR-1 不双领 | 单行条件更新（INV-1） | **无关**。多副本用不同规则同时判定可领，CAS 仍只有一个成功 |
| CR-3 不超卖 | 领取阶段独立容量断言（INV-20） | **无关**。容量校验不经由可扩展规则 |

> INV-20 这条纵深防御顺带消除了「策略切换破坏正确性」的风险。**这是本决策得以选择轻量方案的根本原因。**

### 真正的两个风险

| 风险 | 机理 | 处置 |
|------|------|------|
| **A. 单次领取内混用版本** | 「粗过滤是过度近似」（INV-17）**仅在同一版本内部成立**。若用 v1 取候选、v2 做判定，该关系不存在 ⇒ 本可领取的任务被漏掉，表现为「任务莫名卡在待领取」 | **禁止**，见 INV-37 |
| **B. 收紧型变更在窗口期失效** | 窗口期内旧版本更宽松 ⇒ 按新规则不该被领取的任务仍被领取 | 按变更类型分级处置（见下） |

### 按变更类型分级

| 变更类型 | 窗口期内旧规则的行为 | 后果 | 所需方案 |
|---------|------------------|------|---------|
| 仅调整 `rank`（排序） | 顺序不同 | 仅影响顺序，不影响可行性 | **版本快照即可** |
| **放宽**（允许更多匹配） | 更严格 | 部分任务暂时领不到，**仅影响效率** | **版本快照即可** |
| **收紧**（新增约束） | 更宽松 | **不该领的被领取**，可能违反业务约束或合规要求 | **双版本取交集**（v1 与 v2 均认可才领取）**或暂停领取后切换** |
| 大范围重写 / 无法判定类型 | 不确定 | 按收紧型处理 | 灰度分流 + 双版本校验 |

> **发布流程要求**：发布匹配器时必须声明变更类型。**无法判定时按收紧型处理。**

### 备选方案

| 方案 | 否决 / 采纳理由 |
|------|---------------|
| **停机切换**（暂停领取 → 全副本加载 → 恢复） | ❌ 默认不采用：需要「全系统暂停领取」的协调机制，而 **D2 已确定无选主组件**。为一次秒级操作引入分布式协调，代价与收益不匹配。**保留为收紧型变更的备选** |
| **请求级版本快照** | ✅ **采纳**：无需停机、无需协调；风险已由 INV-20 与 CAS 兜住 |
| 双版本取交集 | 🔶 **仅用于收紧型变更**：求值开销翻倍，且放宽型变更会延迟生效 |
| 灰度分流（按租户/任务） | 🔶 **可叠加**：与版本快照正交，用于控制爆炸半径 |

### 派生要求

| # | 要求 | 支撑需求 |
|---|------|---------|
| 1 | 每次领取须**记录所用匹配器版本** | OR-5 可审计；事后归因时可判定是哪一版规则导致的结果 |
| 2 | **回滚同样是一次切换**，遵循相同语义与分级规则 | OR-5 |
| 3 | 策略变更**不回溯已领取的任务** | 已领取任务的执行权不因规则变更而失效 |
| 4 | 切换窗口期须有指标可观测（各版本的在用副本数） | OR-3；用于确认窗口已收敛 |

## D13 本期不引入独立查询视图

| | |
|---|---|
| **需求** | FR-4 列表查询、FR-22 read-your-writes、FR-23 滞后可观测、冲突 X11 |
| **定义** | 见 [`spec.md`](../requirements/spec.md) §1.2「独立查询视图」 |
| **结论** | **本期不引入**。查询数据与权威数据**同库、同步维护**（方案谱系中的 L0 或 L1，具体形态由存储设计确定） |
| **代价** | 不支持全文检索与多维聚合统计；查询负载与领取路径**共享同一存储**，慢查询可能影响领取延迟 |
| **收益** | 查询**无滞后**，FR-22 天然满足；单一存储，无同步链路、无对账、无视图重建流程 |

### 冲突的实质：数据量差异，而非吞吐

| 访问模式 | 关心的数据 | 规模 | 组织方式诉求 |
|---------|-----------|------|------------|
| **领取路径** | 仅待领取任务 | **约 1 万条** | 小而热；按可领取条件与排序检索；写频繁（每次领取改状态） |
| **列表查询** | 全部任务历史 | **约 4350 万条**（30 天） | 按提交者聚簇；支持分页、组合筛选、计数；读多写少 |

**两者相差约 4000 倍。** 而写入压力（峰值 70/s）在任何单库方案下均非瓶颈——**因此本决策的依据是数据组织，不是吞吐能力**。

```mermaid
    L3 --> L4["<b>L4</b> 异构存储<br/>搜索 / 分析引擎"]
```

| # | 方案 | 是否独立视图 | 滞后 | 满足 FR-22 的方式 | 适用条件 |
|---|------|------------|------|-----------------|---------|
| **L0** | 同一数据结构加索引 | ❌ 否 | **无** | 天然满足 | 历史量可控、无复杂检索需求 |
| **L1** | 同库分表：待领取热表 + 任务历史表，**同事务写入** | 🔶 逻辑分离 | **无** | 天然满足 | 需隔离两种数据量，但仍要求强一致 |
| **L2** | 同库投影表，**异步维护** | ✅ 是 | 有 | 需 read-your-writes 修补 | 查询模式复杂，愿接受滞后 |
| **L3** | 独立读副本 | ✅ 是 | 有 | 同上 | 需隔离查询负载对领取路径的影响 |
| **L4** | 异构存储（全文检索 / 聚合分析） | ✅ 是 | 有 | 同上 | 需要权威存储不具备的检索能力 |

### 判定维度

按重要性排序。**第 1 项决定是否触碰一致性，是真正的分水岭**：

| # | 维度 | 说明 |
|---|------|------|
| **1** | **同步还是异步维护** | 同步 ⇒ 无滞后但耦合写入路径；异步 ⇒ 有滞后，**必须记录序号（INV-13）且必须处理 FR-22** |
| 2 | 查询模式复杂度 | 仅按提交者/状态/时间筛选 ⇒ L0/L1 足够；需全文检索或多维聚合 ⇒ 需 L4 |
| 3 | 负载隔离诉求 | 是否要求慢查询绝不影响领取路径的可用性 |
| 4 | 保留期差异 | 若查询需保留远超领取所需的时长，分离可简化热数据治理 |
| 5 | 重建能力 | 视图须可从权威数据完全重建（定义中的「派生」属性），否则它就成了权威数据 |

### 决策理由

| 依据 | 说明 |
|------|------|
| **付出的代价换不到当期收益** | 独立视图带来的能力（全文检索、多维聚合、长期归档）**当前无需求**，而代价（滞后、多一套系统、多三类故障模式）立即产生 |
| **FR-22 成本** | 同库同步**天然满足** read-your-writes；异步视图需额外修补机制，属纯粹的额外复杂度 |
| 规模 | 4350 万条在单一关系型存储中属常规量级，索引可胜任 |
| 查询模式 | FR-4 仅要求按提交者 / 状态 / 时间筛选与分页，未要求全文检索或复杂聚合 |
| 一致性 | 避免引入滞后，即避免 INV-13 的序号维护与视图重建流程 |
| **决策可推迟且无返工成本** | 只要守住 FR-22（提交者对自己的任务立即可见），将来任何一层方案均成立 |

### 产品与运维影响（本决策的直接后果）

| 维度 | 本期（不引入） | 若将来引入 |
|------|--------------|-----------|
| 提交后列表可见 | **立即** | 延迟 1~3 秒，需呈现「同步中」状态 |
| 按状态 / 时间 / 提交者筛选 | 支持 | 支持 |
| **全文检索任务内容** | **不支持** | 支持 |
| **多维聚合统计报表** | **不支持**（勉强执行会拖慢系统） | 支持 |
| 长期历史查询（数年） | 不支持 | 支持 |
| 需维护的存储 | **1 套** | 2 套（权威 + 视图） |
| 新增故障模式 | — | 同步滞后、同步中断、视图与权威不一致 |
| **慢查询影响** | ⚠️ **可能拖慢任务领取**（须以查询超时与限流兜底） | 隔离，互不影响 |
| 排障复杂度 | 低（单一真相来源） | 中（须先判断是数据错误还是尚未同步） |

> ⚠️ **本决策引入的唯一新风险**：查询与领取共享存储，**慢查询可能影响领取延迟**。存储设计时须为查询路径设置超时上限与并发限制，避免其挤占领取路径资源。

满足任一即重开本决策（新增 `SUPERSEDED BY` 记录）：

## D18 对话层在任务系统之上：Session 日志与 Turn 领取

| | |
|---|---|
| **需求** | FR-9~FR-15（跨设备查阅、续订、流式渲染）；Agent 多轮会话（`task-profiles` 中 `agent`）及同会话内后续 image/video 等任务 |
| **结论** | ① **Conversation / Session** 是产品 UX 身份，不是 TCP/WS 连接，也不是 Worker 租约。② **Turn（一轮用户输入 + 一次生成）= Task**，Worker **按 Turn 领取**，不按 Session 粘滞领取。③ 客户端面向的可回放真相是 **Session 级 append-only 日志**，序号为 **per-session 单调 seq**（由通道分配）；用户消息、锁/busy、轮次边界、Agent token、图片/视频进度与产物等 **进入同一条 Session 流**（方案 A）。④ **开屏靠带 `snapshot_seq` 的渲染快照 + 增量**，禁止靠全量回放 TextDelta。⑤ **占用锁为 Session 级 CAS**（当前策略 `max_in_flight_turns_per_session = 1`）；禁止态以流上的 busy/idle 事件为准，不用 presence。⑥ **同一 Session** 同时订阅者预期 **≤ 5**（非全产品人少）：不做分层扇出，Realtime 实例内 1 路订阅复用即可。⑦ 写入侧 TextDelta **聚合窗口本期不定**（配置项，非架构锁）。⑧ **有效 Session 日志始终可订**；热层可卸载到冷存储；热 miss 须明确报错并导向快照/冷层（INV-14）。⑨ **跨区**：一期 Realtime 就近 + **读回源**；二期 Mirror 仅实测触发。⑩ 绿场第一热层适配器 **Redis Streams**（JetStream 留作副本阶段选项）。 |
| **代价** | Session 热层事件量高于「仅信封」方案；必须维护快照与可合并标记（INV-16），否则开屏与存储会被 token 洪水打穿 |
| **素材** | [`../design/drafts/conversation.md`](../design/drafts/conversation.md)（草稿）· [`../design/drafts/stream-channel-adapters.md`](../design/drafts/stream-channel-adapters.md)（Redis vs JetStream 选型对比） |

**已拍板的三轴（选型前置）**

| 轴 | 结论 |
|----|------|
| 日志 vs 广播 | **必须是可回放日志**（ChatBot / Agent 会话） |
| 序号命名空间 | **按 Session 编排**，不是按 Task；一个 Session 可含多个 Agent / image / video Turn |
| 扇出 | 同 Session ≤ 5 订阅者 → **无需分层扇出** |

**与 INV-10 / INV-12 的关系（用语澄清，非废止）**

- INV-10 的「流身份 = `task_id`」约束的是：**任务执行输出与 attempt/fence 的绑定**，以及「以单任务为观测单元」时的共享续订。多轮对话的 **客户端重放游标** 是 `(session_id, last_seq)`（见 INV-12 澄清）。
- 每条 Session 流事件仍携带 `task_id` / `message_id` / `attempt`，供 CR-4 隔离与 UI 分组；**不得**把整段 Session 领给一台 Worker。
- INV-12 禁止的是服务端 **连接粘性 / 连接级游标**；**允许** Session 作为领域资源（元数据、锁、快照）。

**并行 Turn（当前否、将来可）**

- **当前**：同一 Session 不可并行多个 Turn（一把 generation 锁）。
- **将来**若放开：不改 Session 日志与 StreamChannel 主轴；改为锁策略（`max_in_flight > 1`）、快照 `running[]`、UI 按 `message_id` 分组。事件从第一天起即带 `message_id` + `task_id`，避免返工。

**碎片化处置（方案 A 的配套，非另选 B）**

| 层 | 手段 |
|----|------|
| 写入 | TextDelta / Progress 可配置聚合（窗口本期不定） |
| 开屏 | 快照中已折叠历史气泡；只追 `snapshot_seq` 之后增量 |
| 读路径 | `coalescible` 事件可丢中间态；信封类不可丢（INV-16） |

**StreamChannel 选型方向（适配器，非产品锁定；D14）**

- 端口语义：可回放 WAL；`append` 内部分配 **per-stream（Session）连续 seq**；扇出与快照 **不进** 本端口。
- **绿场、无既有 Redis/NATS**：第一套生产适配器定为 **Redis Streams**（与 per-session 短流同构、编码薄、与领取路径分离落实 D11）。对外游标 **禁止** 暴露 JetStream 全局 stream seq。
- **JetStream** 为预留替换/并行选项，主要加分在跨区 **Mirror 副本**阶段，而非一期必选。Kafka 仅在事件速率逼近越界线时评估。
- L0–L2 继续 mem（D17）。端口键需从仅 `TaskId` **泛化为 `StreamId`（含 session）**——属观测/对话设计步骤，不插队迭代 1 存储选型之前强制实现。

**保留与热→冷（纠正「淘汰=可丢弃」）**

- **有效 Session 日志在业务上须始终可订可读**（含任意时刻打开历史对话）。
- 热层（Redis Streams / 将来的 JetStream）可按成本做 **卸载**：归档到冷存储（对象存储等）后从热层移除。
- INV-14 的含义是：热层已无该 `from_seq` 时 **必须明确报错 / 引导**，客户端改走 **快照或冷层**，**禁止**静默从「还能读到的最早热数据」续发。**不是**允许业务丢弃历史。
- `parameters.md` 中的「输出保留期 7 天」等数字，在对话层语境下解释为 **热层成本锚点**，不是「7 天后内容作废」。冷层保留策略可另定，但不得使有效 Session 无法恢复。

**跨区订阅分期（不与 D8 领取单域混为一谈）**

观测跨区与领取权威是否单域是不同问题。对话/观测路径按下列顺序推进（**已对齐**）：

| 阶段 | 做法 | 产品含义 |
|------|------|----------|
| **正确性先行** | Session 可回放日志 + 快照 + 热→冷 | 与选 Redis/JetStream 无关 |
| **跨区一期** | Realtime **就近接入**，读路径 **回源**（外区 RG 向写入权威区拉/订同一条 Session 流） | 外区用户能订；源区流存储不可用则外区热订不可用 |
| **跨区二期** | 仅当实测跨区延迟或源区故障影响不可接受时，加 **Mirror/本地只读副本** | 源区短暂故障时外区仍可读已复制部分；就近读 |

- 一期 **不**为 Mirror 提前锁定 JetStream。
- 二期：若热层已是 JetStream，Mirror 叙事更顺；若仍是 Redis，则上复制方案或按 D14 **换/加** JetStream 适配器。客户端游标始终为 `(session_id, session_seq)`。

**扇出用语**：上表「≤ 5」指 **同一 Session 的同时订阅连接数**，不是全产品观测用户少。全站仍可有大量连接（多 Session × 每 Session 很少人）。

**Redis Streams vs JetStream：性能与成本（选型理由补强，非不可适应性）**

两者对 D18 契约（可回放、per-session seq、热→冷）**均可适配**；一期选 Redis 是模型同构与工程薄，不是 JetStream「不能用」。

| 维度 | Redis Streams（多本账） | JetStream（大河 + subject filter） |
|------|-------------------------|-------------------------------------|
| 读本 Session | 只碰该 key；与全站总量基本无关 | 实时 interest 通常轻；**长距离**按 Session filter 追平可能在大河里大量 skip |
| 成本形态 | 热数据偏 **内存** | 热数据偏 **磁盘日志** |
| 一期（回源、热窗口短、开屏靠快照） | 更贴「一 Session 一账」 | 亦可；须保证 catch-up 距离有上界 |
| 二期 Mirror | 复制方案要自证 | Mirror 叙事更成熟 |

**必须守住的性能前提**（与选谁无关）：开屏 = 快照 + **短**增量；禁止无快照地从很老的 seq 在共享大河里全量 filter 回放。有此前提后，filter「跳过税」通常可忽略；无此前提则 JetStream 大河模型会在数据量大时恶化。

**否决**

| 方案 | 否决理由 |
|------|---------|
| Session = 长期领取给一台 Worker | 占容量、与 D9 冲突；跨设备查阅不需要执行亲和 |
| 对话 = Room = 单个 Task（旧观测草稿） | 多轮 / 多类型任务揉进一个 `task_id`，重试与容量账本变形 |
| CRDT / 仅 PubSub / sticky 连接会话 | 破坏全序、不可续订、或违反 INV-12 |
| 开屏全量回放 token | 违反 FR-10 / INV-13 精神；切换 Session 不可用 |
| presence 当禁止态 | 不可靠；必须以 CAS + 流事件为准 |
| 热层 trim 后静默丢历史且无冷层出口 | 违反「有效 Session 始终可订」；INV-14 必须导向快照/冷层 |

**备选方案**

| 方案 | 否决 / 推迟理由 |
|------|----------------|
| Session 日志仅信封，token 挂在 task 流（方案 B） | 开屏需订双流、并发时间线需自拼；与「Session 级重放」决策不符。若聚合+快照无法压住成本，可再开 `SUPERSEDED BY` 评估 |
| 全局一条大河 seq（原生 JetStream seq 暴露给客户端） | 与 Session 游标决策冲突；不作为默认 |
| 第一期即 Mirror | 实现与运维成本高；回源已满足「跨区能订」；仅实测不够时进入二期 |
| 以 D8 或「7 天可丢」为由排除 JetStream / 排除跨区观测 | **已纠正**：D8 管领取权威；保留是热→冷；跨区观测按上表分期 |

**落地顺序**：不插队。依赖路线图「存储 → 生命周期/事件 → 观测与协作（改写 observation + 并入本决策）」。跨区一期回源、二期副本见上表。详见 [`../plans/conversation-and-stream.md`](../plans/conversation-and-stream.md) · [`../plans/README.md`](../plans/README.md)。
