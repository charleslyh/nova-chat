## D1 容量模型不在架构层锁定

| | |
|---|---|
| **需求** | FR-2.1 容量感知、FR-2.6 容量模型可扩展 |
| **结论** | 不预设容量维度。抽象为「匹配器」，匹配规则以受限 DSL 表达，可不停机替换 |
| **代价** | 引入代码执行入口 ⇒ 派生 SEC-6（沙箱）与 INV-17~INV-20 |

**理由**：容量形态（标量 / 向量 / 附带标签）在需求阶段无法确定，锁定任一形态都会在业务演进时引发核心流程改造。

**成立前提**：由 D3 支付。任意 DSL 谓词**无法下推到索引**，只能「取候选逐条求值」。池 < 1 万时该成本可忽略；若池达 1e7 量级，此决策不成立。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| 锁定单维标量 | 无法表达标签约束与多维容量，业务演进即需改造核心 |
| 锁定多维向量 | 过度设计；且仍无法表达非数值型约束 |

## D2 匹配采用 first-fit + 设备自主拉取

| | |
|---|---|
| **需求** | FR-2.3 无队头阻塞、SR-1 水平扩容 |
| **结论** | 设备主动拉取，扫描候选窗口，**满足即领取**，不追求最优装箱 |
| **代价** | 装箱非最优（范围界定 S2 已接受） |

**理由**：first-fit 使匹配决策**完全本地化**，无需中心组件掌握全局视图。这直接消除了中心调度器及其选主机制。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| best-fit（设备扫窗口选最贴合） | 装箱略优，但需更大候选窗口；当前装箱率目标 70% 无需此优化 |
| 全局最优（中心调度器统一分配） | **需选主**，且成为吞吐瓶颈与单点。装箱收益不足以抵偿复杂度 |

## D3 规模按 DAU 50 万为设计基准

| | |
|---|---|
| **依据** | `parameters.md` §2 锚点、§4 导出量 |
| **结论** | 池 < 1 万、峰值领取 70/s、并发任务 2.1 万、设备 1.05 万；适用区间取 5~14 倍 |

**理由**：DAU 是唯一可观测的业务锚点，其余参数由守恒关系导出（§3）。规模不可预估时，以「适用区间 + 越界阈值」替代精确值。

**关键推论**：此规模使 D1（DSL 逐条求值）与单一强一致判定点均成立。**D3 越界会同时动摇 D1 与 D2。**

## D4 领取不跨区域

| | |
|---|---|
| **需求** | 冲突 X5（CR-1 领取唯一性 × FR-1 多区域低延迟） |
| **结论** | 任务与执行设备按区域绑定，领取判定不跨区域 |

**理由**：唯一性判定必须集中，跨区域领取会在关键路径引入区域间往返延迟（< 200ms）。区域内绑定使 X5 无需仲裁。

> **注意**：这不影响 FR-11（跨区域观测）——**观测是读路径，与领取解耦**。

## D5 防饥饿采用老化 + 定向预留排水

| | |
|---|---|
| **需求** | FR-2.4、`spec.md` §3.2 两类饥饿 |
| **结论** | 排序型饥饿用排序老化；**容量型饥饿用定向预留 + 排水** |
| **代价** | 排水期间容量闲置，装箱率下降（冲突 X2，由装箱率目标 70% 仲裁） |

**理由**：**老化只能解决排序型饥饿。** 容量型饥饿（需求 8 而剩余恒为 4）中任务不可行，排到第一也领不走，必须阻止小任务继续占用容量。

**成立前提**：依赖 D9 的静态执行上界为排水时间提供确定上界。若执行时长无界，则排水时间无界，FR-2.4 不可验收。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| 仅做老化 | **不满足 FR-2.4**，遗留一类永不执行的任务 |
| 全局屏障（停止所有小任务派发） | 影响面过大，吞吐损失远超定向预留 |

## D6 不做抢占

| | |
|---|---|
| **结论** | 高优先级任务不中断已在执行的任务（范围界定 S4） |
| **代价** | 高优先级任务的等待时长受在途任务时长影响 |

## D8 单域起步

| | |
|---|---|
| **结论** | 单一区域承担任务权威状态，不做容灾切换（范围界定 S6） |
| **代价** | 该区域故障时提交与领取不可用（可用性目标 99.9% 可接受） |

**理由**：D4 已确定领取不跨区域，多域的主要价值（容灾）需要跨域一致性协议与故障转移，复杂度与当前可用性目标不匹配。

> **观测层仍是多区域的**：观测者可就近接入（FR-11），因为读路径无一致性要求。

## D9 不做任务级执行权时限与续期

| | |
|---|---|
| **需求** | FR-18 失联回收、SR-4 长耗时任务、冲突 X14 |
| **结论** | **设备级存活信号**（每设备一个）+ **任务静态执行时长上界**（领取时写定，永不更新） |
| **代价** | 任务卡死的发现延迟至执行上界（4 小时），而非一个续期周期 |

**理由**

| 维度 | 本决策 | 任务级时限 + 续期 |
|------|-------|------------------|
| 需维护的时限对象 | 每设备 1 个 | **每在途任务 1 个** |
| 续期逻辑 | **无** | 需要，且需防误判 |
| 长耗时任务风险 | 低（判定与任务时长无关） | **高**——续期间隔配错、执行线程阻塞均会**误杀正在正常执行的任务**，与 SR-4 直接冲突 |

**关键洞察**：续期机制的失败模式是「破坏正确性」（误杀正常任务），而本决策下自检失败的后果仅为「浪费算力」。**故障模式严重性降级是本决策的主要收益，而非仅是简化。**

**派生约束**

- 自检必须只读（INV-7），否则退化为续期
- 执行上界必须静态（INV-9），否则等价于续期，且排水时间失去上界
- **尝试序号仍必须存在**（INV-5）——它是 CR-4/CR-8 的唯一依据，且本就承担 FR-6 重试计数

**后续引入条件**（满足任一）

- 卡死频率使「等到执行上界」的资源浪费不可接受
- 需区分「设备健康」与「单任务健康」以支撑更细的调度
- 单设备并发任务数升高，使设备级回收的影响面过大

## D10 容量账本由服务端核算

| | |
|---|---|
| **需求** | CR-3 容量不超卖、CR-10 容量账目可信 |
| **结论** | 执行设备只上报**静态总容量**与存活信号；**剩余容量由服务端按在途任务聚合推算** |
| **代价** | 领取时需一次聚合查询（D3 规模下成本可忽略） |

**理由**：若采信设备自报的剩余容量，**设备谎报即可绕过容量约束，FR-2.1 形同虚设**。容量账本必须在服务端，这是 CR-10 的唯一实现路径。

**备选方案**

| 方案 | 否决理由 |
|------|---------|
| 设备自报剩余容量 | **不满足 CR-10**；容量约束可被绕过 |
| 设备自报 + 服务端抽查 | 抽查窗口内仍可超卖，且复杂度高于直接核算 |

## D11 领取路径与输出路径分离

| | |
|---|---|
| **依据** | `parameters.md` 输出事件 vs meta CAS 数量级（原任务领取口径；D19 后为 meta vs stream） |
| **结论** | **meta（Session 锁 / Turn claim）与 stream（Session 事件 append）不共用同一承载** |
| **澄清（D19）** | 本决策约束**存储路径**，不要求 HTTP POST 与 SSE 分进程 |

**理由（量化）**：提交/claim ~70/s 量级强一致；流事件 ~2 万条/s 保序。同承载会互相拖死。

> **这是由量化数据强制得出的分层**，而非「两个接入服务」偏好。

> **RESTATED BY D21（2026-09-01）**：本决策**未被废止**，结论完全不变。仅路径名称随 D20 边界收口而更新——分承载的两侧由「会话锁 / 轮次领取 vs 会话事件日志」改述为「**低频上下文库与账本（~70/s，强一致）vs 高频在途事件缓冲（~2 万条/s，保序）**」。两侧仍相差约三个数量级，仍必须分承载；具体承载分工见 D21。

## D12 策略切换采用请求级版本快照

| | |
|---|---|
| **需求** | FR-19 不停机调整策略、OR-5 变更可审计可回滚、冲突 X13 |
| **结论** | ① 单次领取全程使用**同一版本**的匹配器（版本快照）；② **允许不同副本短暂持有不同版本**；③ **收紧型变更**须额外采取双版本校验或暂停切换 |
| **代价** | 切换窗口期内（配置传播时长，秒级）不同副本按不同 `rank` 排序，FR-2.2 优先级偏序**短暂降级** |

### 前提修正：切换期不威胁 CR-1 / CR-3

冲突矩阵 X13 最初判断策略切换会威胁 CR-1（不双领）与 CR-3（不超卖）。**该判断不成立**：

| 需求 | 实际保证者 | 与匹配规则的关系 |
|------|-----------|----------------|
| CR-1 不双领 | 单行条件更新（INV-1） | **无关**。多副本用不同规则同时判定可领，CAS 仍只有一个成功 |
| CR-3 不超卖 | 领取阶段独立容量断言（INV-20） | **无关**。容量校验不经由可扩展规则 |

> INV-20 这条纵深防御顺带消除了「策略切换破坏正确性」的风险。**这是本决策得以选择轻量方案的根本原因。**

### 真正的两个风险

| 风险 | 机理 | 处置 |
|------|------|------|
| **A. 单次领取内混用版本** | 「粗过滤是过度近似」（INV-17）**仅在同一版本内部成立**。若用 v1 取候选、v2 做判定，该关系不存在 ⇒ 本可领取的任务被漏掉，表现为「任务莫名卡在待领取」 | **禁止**，见 INV-37 |
| **B. 收紧型变更在窗口期失效** | 窗口期内旧版本更宽松 ⇒ 按新规则不该被领取的任务仍被领取 | 按变更类型分级处置（见下） |

### 按变更类型分级

| 变更类型 | 窗口期内旧规则的行为 | 后果 | 所需方案 |
|---------|------------------|------|---------|
| 仅调整 `rank`（排序） | 顺序不同 | 仅影响顺序，不影响可行性 | **版本快照即可** |
| **放宽**（允许更多匹配） | 更严格 | 部分任务暂时领不到，**仅影响效率** | **版本快照即可** |
| **收紧**（新增约束） | 更宽松 | **不该领的被领取**，可能违反业务约束或合规要求 | **双版本取交集**（v1 与 v2 均认可才领取）**或暂停领取后切换** |
| 大范围重写 / 无法判定类型 | 不确定 | 按收紧型处理 | 灰度分流 + 双版本校验 |

> **发布流程要求**：发布匹配器时必须声明变更类型。**无法判定时按收紧型处理。**

### 备选方案

| 方案 | 否决 / 采纳理由 |
|------|---------------|
| **停机切换**（暂停领取 → 全副本加载 → 恢复） | ❌ 默认不采用：需要「全系统暂停领取」的协调机制，而 **D2 已确定无选主组件**。为一次秒级操作引入分布式协调，代价与收益不匹配。**保留为收紧型变更的备选** |
| **请求级版本快照** | ✅ **采纳**：无需停机、无需协调；风险已由 INV-20 与 CAS 兜住 |
| 双版本取交集 | 🔶 **仅用于收紧型变更**：求值开销翻倍，且放宽型变更会延迟生效 |
| 灰度分流（按租户/任务） | 🔶 **可叠加**：与版本快照正交，用于控制爆炸半径 |

### 派生要求

| # | 要求 | 支撑需求 |
|---|------|---------|
| 1 | 每次领取须**记录所用匹配器版本** | OR-5 可审计；事后归因时可判定是哪一版规则导致的结果 |
| 2 | **回滚同样是一次切换**，遵循相同语义与分级规则 | OR-5 |
| 3 | 策略变更**不回溯已领取的任务** | 已领取任务的执行权不因规则变更而失效 |
| 4 | 切换窗口期须有指标可观测（各版本的在用副本数） | OR-3；用于确认窗口已收敛 |

## D13 本期不引入独立查询视图

| | |
|---|---|
| **需求** | FR-4 列表查询、FR-22 read-your-writes、FR-23 滞后可观测、冲突 X11 |
| **定义** | 见 [`spec.md`](../requirements/spec.md) §1.2「独立查询视图」 |
| **结论** | **本期不引入**。查询数据与权威数据**同库、同步维护**（方案谱系中的 L0 或 L1，具体形态由存储设计确定） |
| **代价** | 不支持全文检索与多维聚合统计；查询负载与领取路径**共享同一存储**，慢查询可能影响领取延迟 |
| **收益** | 查询**无滞后**，FR-22 天然满足；单一存储，无同步链路、无对账、无视图重建流程 |

### 冲突的实质：数据量差异，而非吞吐

| 访问模式 | 关心的数据 | 规模 | 组织方式诉求 |
|---------|-----------|------|------------|
| **领取路径** | 仅待领取任务 | **约 1 万条** | 小而热；按可领取条件与排序检索；写频繁（每次领取改状态） |
| **列表查询** | 全部任务历史 | **约 4350 万条**（30 天） | 按提交者聚簇；支持分页、组合筛选、计数；读多写少 |

**两者相差约 4000 倍。** 而写入压力（峰值 70/s）在任何单库方案下均非瓶颈——**因此本决策的依据是数据组织，不是吞吐能力**。

### 方案谱系（不是二元选择）

```mermaid
%%{init: {"flowchart": {"curve": "basis", "rankSpacing": 80, "nodeSpacing": 26}}}%%
flowchart LR
    L0["<b>L0</b> 同表加索引<br/><i>不构成独立视图</i>"] --> L1["<b>L1</b> 同库分表<br/>热表 + 历史表"]
    L1 --> L2["<b>L2</b> 同库投影表<br/>异步维护"]
    L2 --> L3["<b>L3</b> 独立读副本"]
    L3 --> L4["<b>L4</b> 异构存储<br/>搜索 / 分析引擎"]
```

| # | 方案 | 是否独立视图 | 滞后 | 满足 FR-22 的方式 | 适用条件 |
|---|------|------------|------|-----------------|---------|
| **L0** | 同一数据结构加索引 | ❌ 否 | **无** | 天然满足 | 历史量可控、无复杂检索需求 |
| **L1** | 同库分表：待领取热表 + 任务历史表，**同事务写入** | 🔶 逻辑分离 | **无** | 天然满足 | 需隔离两种数据量，但仍要求强一致 |
| **L2** | 同库投影表，**异步维护** | ✅ 是 | 有 | 需 read-your-writes 修补 | 查询模式复杂，愿接受滞后 |
| **L3** | 独立读副本 | ✅ 是 | 有 | 同上 | 需隔离查询负载对领取路径的影响 |
| **L4** | 异构存储（全文检索 / 聚合分析） | ✅ 是 | 有 | 同上 | 需要权威存储不具备的检索能力 |

### 判定维度

按重要性排序。**第 1 项决定是否触碰一致性，是真正的分水岭**：

| # | 维度 | 说明 |
|---|------|------|
| **1** | **同步还是异步维护** | 同步 ⇒ 无滞后但耦合写入路径；异步 ⇒ 有滞后，**必须记录序号（INV-13）且必须处理 FR-22** |
| 2 | 查询模式复杂度 | 仅按提交者/状态/时间筛选 ⇒ L0/L1 足够；需全文检索或多维聚合 ⇒ 需 L4 |
| 3 | 负载隔离诉求 | 是否要求慢查询绝不影响领取路径的可用性 |
| 4 | 保留期差异 | 若查询需保留远超领取所需的时长，分离可简化热数据治理 |
| 5 | 重建能力 | 视图须可从权威数据完全重建（定义中的「派生」属性），否则它就成了权威数据 |

### 决策理由

| 依据 | 说明 |
|------|------|
| **付出的代价换不到当期收益** | 独立视图带来的能力（全文检索、多维聚合、长期归档）**当前无需求**，而代价（滞后、多一套系统、多三类故障模式）立即产生 |
| **FR-22 成本** | 同库同步**天然满足** read-your-writes；异步视图需额外修补机制，属纯粹的额外复杂度 |
| 规模 | 4350 万条在单一关系型存储中属常规量级，索引可胜任 |
| 查询模式 | FR-4 仅要求按提交者 / 状态 / 时间筛选与分页，未要求全文检索或复杂聚合 |
| 一致性 | 避免引入滞后，即避免 INV-13 的序号维护与视图重建流程 |
| **决策可推迟且无返工成本** | 只要守住 FR-22（提交者对自己的任务立即可见），将来任何一层方案均成立 |

### 产品与运维影响（本决策的直接后果）

| 维度 | 本期（不引入） | 若将来引入 |
|------|--------------|-----------|
| 提交后列表可见 | **立即** | 延迟 1~3 秒，需呈现「同步中」状态 |
| 按状态 / 时间 / 提交者筛选 | 支持 | 支持 |
| **全文检索任务内容** | **不支持** | 支持 |
| **多维聚合统计报表** | **不支持**（勉强执行会拖慢系统） | 支持 |
| 长期历史查询（数年） | 不支持 | 支持 |
| 需维护的存储 | **1 套** | 2 套（权威 + 视图） |
| 新增故障模式 | — | 同步滞后、同步中断、视图与权威不一致 |
| **慢查询影响** | ⚠️ **可能拖慢任务领取**（须以查询超时与限流兜底） | 隔离，互不影响 |
| 排障复杂度 | 低（单一真相来源） | 中（须先判断是数据错误还是尚未同步） |

> ⚠️ **本决策引入的唯一新风险**：查询与领取共享存储，**慢查询可能影响领取延迟**。存储设计时须为查询路径设置超时上限与并发限制，避免其挤占领取路径资源。

### 重新评估的触发条件

满足任一即重开本决策（新增 `SUPERSEDED BY` 记录）：

| # | 触发条件 | 判定方式 |
|---|---------|---------|
| 1 | 产品需要**全文检索**任务内容或**数据报表** | 产品需求提出即触发 |
| 2 | **实测**发现查询负载影响领取路径延迟 | 领取延迟 P99 与查询负载相关性可观测（须有数据，不接受预判） |

## D18 对话层在任务系统之上：Session 日志与 Turn 领取

| | |
|---|---|
| **需求** | FR-9~FR-15（跨设备查阅、续订、流式渲染）；多轮 Session（任务系统时代画像已归档） |
| **结论** | ① **Conversation / Session** 是产品 UX 身份，不是 TCP/WS 连接，也不是 Worker 租约。② **Turn（一轮用户输入 + 一次生成）= Task**，Worker **按 Turn 领取**，不按 Session 粘滞领取。③ 客户端面向的可回放真相是 **Session 级 append-only 日志**，序号为 **per-session 单调 seq**（由通道分配）；用户消息、锁/busy、轮次边界、Agent token、图片/视频进度与产物等 **进入同一条 Session 流**（方案 A）。④ **开屏靠带 `snapshot_seq` 的渲染快照 + 增量**，禁止靠全量回放 TextDelta。⑤ **占用锁为 Session 级 CAS**（当前策略 `max_in_flight_turns_per_session = 1`）；禁止态以流上的 busy/idle 事件为准，不用 presence。⑥ **同一 Session** 同时订阅者预期 **≤ 5**（非全产品人少）：不做分层扇出，订路径实例内 1 路订阅复用即可。⑦ 写入侧 TextDelta **聚合窗口本期不定**（配置项，非架构锁）。⑧ **有效 Session 日志始终可订**；热层可卸载到冷存储；热 miss 须明确报错并导向快照/冷层（INV-14）。⑨ **跨区**：一期就近接入 + **读回源**；二期 Mirror 仅实测触发。⑩ 绿场第一热层适配器 **Redis Streams**（JetStream 留作副本阶段选项）。 |
| **代价** | Session 热层事件量高于「仅信封」方案；必须维护快照与可合并标记（INV-16），否则开屏与存储会被 token 洪水打穿 |
| **素材** | 已归档草稿（`archive/draft-conversation.md` 等）· [`../design/drafts/stream-channel-adapters.md`](../design/drafts/stream-channel-adapters.md)（Redis vs JetStream） |

**已拍板的三轴（选型前置）**

| 轴 | 结论 |
|----|------|
| 日志 vs 广播 | **必须是可回放日志**（ChatBot / Agent 会话） |
| 序号命名空间 | **按 Session 编排**，不是按 Task；一个 Session 可含多个 Agent / image / video Turn |
| 扇出 | 同 Session ≤ 5 订阅者 → **无需分层扇出** |

**与 INV-10 / INV-12 的关系（用语澄清，非废止）**

- INV-10 的「流身份 = `task_id`」约束的是：**任务执行输出与 attempt/fence 的绑定**，以及「以单任务为观测单元」时的共享续订。多轮对话的 **客户端重放游标** 是 `(session_id, last_seq)`（见 INV-12 澄清）。
- 每条 Session 流事件仍携带 `task_id` / `message_id` / `attempt`，供 CR-4 隔离与 UI 分组；**不得**把整段 Session 领给一台 Worker。
- INV-12 禁止的是服务端 **连接粘性 / 连接级游标**；**允许** Session 作为领域资源（元数据、锁、快照）。

**并行 Turn（当前否、将来可）**

- **当前**：同一 Session 不可并行多个 Turn（一把 generation 锁）。
- **将来**若放开：不改 Session 日志与 StreamChannel 主轴；改为锁策略（`max_in_flight > 1`）、快照 `running[]`、UI 按 `message_id` 分组。事件从第一天起即带 `message_id` + `task_id`，避免返工。

**碎片化处置（方案 A 的配套，非另选 B）**

| 层 | 手段 |
|----|------|
| 写入 | TextDelta / Progress 可配置聚合（窗口本期不定） |
| 开屏 | 快照中已折叠历史气泡；只追 `snapshot_seq` 之后增量 |
| 读路径 | `coalescible` 事件可丢中间态；信封类不可丢（INV-16） |

**StreamChannel 选型方向（适配器，非产品锁定；D14）**

- 端口语义：可回放 WAL；`append` 内部分配 **per-stream（Session）连续 seq**；扇出与快照 **不进** 本端口。
- **绿场、无既有 Redis/NATS**：第一套生产适配器定为 **Redis Streams**（与 per-session 短流同构、编码薄、与领取路径分离落实 D11）。对外游标 **禁止** 暴露 JetStream 全局 stream seq。
- **JetStream** 为预留替换/并行选项，主要加分在跨区 **Mirror 副本**阶段，而非一期必选。Kafka 仅在事件速率逼近越界线时评估。
- L0–L2 继续 mem（D17）。端口键需从仅 `TaskId` **泛化为 `StreamId`（含 session）**——属观测/对话设计步骤，不插队迭代 1 存储选型之前强制实现。

**保留与热→冷（纠正「淘汰=可丢弃」）**

- **有效 Session 日志在业务上须始终可订可读**（含任意时刻打开历史对话）。
- 热层（Redis Streams / 将来的 JetStream）可按成本做 **卸载**：归档到冷存储（对象存储等）后从热层移除。
- INV-14 的含义是：热层已无该 `from_seq` 时 **必须明确报错 / 引导**，客户端改走 **快照或冷层**，**禁止**静默从「还能读到的最早热数据」续发。**不是**允许业务丢弃历史。
- `parameters.md` 中的「输出保留期 7 天」等数字，在对话层语境下解释为 **热层成本锚点**，不是「7 天后内容作废」。冷层保留策略可另定，但不得使有效 Session 无法恢复。

**跨区订阅分期（不与 D8 领取单域混为一谈）**

观测跨区与领取权威是否单域是不同问题。对话/观测路径按下列顺序推进（**已对齐**）：

| 阶段 | 做法 | 产品含义 |
|------|------|----------|
| **正确性先行** | Session 可回放日志 + 快照 + 热→冷 | 与选 Redis/JetStream 无关 |
| **跨区一期** | 就近接入同一服务（`nova-sessions`），读路径 **回源**（外区向写入权威区拉/订同一条 Session 流） | 外区用户能订；源区流存储不可用则外区热订不可用 |
| **跨区二期** | 仅当实测跨区延迟或源区故障影响不可接受时，加 **Mirror/本地只读副本** | 源区短暂故障时外区仍可读已复制部分；就近读 |

- 一期 **不**为 Mirror 提前锁定 JetStream。
- 二期：若热层已是 JetStream，Mirror 叙事更顺；若仍是 Redis，则上复制方案或按 D14 **换/加** JetStream 适配器。客户端游标始终为 `(session_id, session_seq)`。

**扇出用语**：上表「≤ 5」指 **同一 Session 的同时订阅连接数**，不是全产品观测用户少。全站仍可有大量连接（多 Session × 每 Session 很少人）。

**Redis Streams vs JetStream：性能与成本（选型理由补强，非不可适应性）**

两者对 D18 契约（可回放、per-session seq、热→冷）**均可适配**；一期选 Redis 是模型同构与工程薄，不是 JetStream「不能用」。

| 维度 | Redis Streams（多本账） | JetStream（大河 + subject filter） |
|------|-------------------------|-------------------------------------|
| 读本 Session | 只碰该 key；与全站总量基本无关 | 实时 interest 通常轻；**长距离**按 Session filter 追平可能在大河里大量 skip |
| 成本形态 | 热数据偏 **内存** | 热数据偏 **磁盘日志** |
| 一期（回源、热窗口短、开屏靠快照） | 更贴「一 Session 一账」 | 亦可；须保证 catch-up 距离有上界 |
| 二期 Mirror | 复制方案要自证 | Mirror 叙事更成熟 |

**必须守住的性能前提**（与选谁无关）：开屏 = 快照 + **短**增量；禁止无快照地从很老的 seq 在共享大河里全量 filter 回放。有此前提后，filter「跳过税」通常可忽略；无此前提则 JetStream 大河模型会在数据量大时恶化。

**否决**

| 方案 | 否决理由 |
|------|---------|
| Session = 长期领取给一台 Worker | 占容量、与 D9 冲突；跨设备查阅不需要执行亲和 |
| 对话 = Room = 单个 Task（旧观测草稿） | 多轮 / 多类型任务揉进一个 `task_id`，重试与容量账本变形 |
| CRDT / 仅 PubSub / sticky 连接会话 | 破坏全序、不可续订、或违反 INV-12 |
| 开屏全量回放 token | 违反 FR-10 / INV-13 精神；切换 Session 不可用 |
| presence 当禁止态 | 不可靠；必须以 CAS + 流事件为准 |
| 热层 trim 后静默丢历史且无冷层出口 | 违反「有效 Session 始终可订」；INV-14 必须导向快照/冷层 |

**备选方案**

| 方案 | 否决 / 推迟理由 |
|------|----------------|
| Session 日志仅信封，token 挂在 task 流（方案 B） | 开屏需订双流、并发时间线需自拼；与「Session 级重放」决策不符。若聚合+快照无法压住成本，可再开 `SUPERSEDED BY` 评估 |
| 全局一条大河 seq（原生 JetStream seq 暴露给客户端） | 与 Session 游标决策冲突；不作为默认 |
| 第一期即 Mirror | 实现与运维成本高；回源已满足「跨区能订」；仅实测不够时进入二期 |
| 以 D8 或「7 天可丢」为由排除 JetStream / 排除跨区观测 | **已纠正**：D8 管领取权威；保留是热→冷；跨区观测按上表分期 |

**落地顺序**：不插队。跨区一期回源、二期副本见上表。现行推进见 [`../plans/current.md`](../plans/current.md) · [`../plans/README.md`](../plans/README.md)。

> **SUPERSEDED IN PART BY D19（2026-08-27）**：废止「Turn = Task / 任务系统之上」的产品定位；Session 可回放日志、快照、游标、跨区回源、热→冷、Redis Streams 默认等契约由 D19 继承并升格为产品主轴。文中「Realtime」指订路径能力，**不是**独立服务身份。
>
> **SUPERSEDED IN PART BY D20（2026-09-01）**：进一步废止 ①（Session 作为领域资源）、③（跨轮次 Session 级 append-only 日志与 per-session 序号）、④（`snapshot_seq` 渲染快照开屏）、⑤（Session 级占用锁与 busy/idle 事件）、⑥（同 Session 多订阅者扇出）、⑧（热→冷卸载与冷层回读）、⑨（跨区回源与 Mirror 二期）。序号命名空间由 Session 收敛为**单次生成**且改为 0 基连续；开屏能力取消；多轮上下文改由 `previous_response_id` 走链拼接（D20）。⑦（增量事件聚合窗口为配置项）与 ⑩ 中「热层选型属适配器而非产品锁定」继续生效，后者的具体选型理由归入 D21。

## D20 交付边界收口：存储与订阅分离

| | |
|---|---|
| **需求** | [`spec.md`](../requirements/spec.md) v3：单次生成流式服务 + 服务端上下文寻回 |
| **结论** | ① 对外**主资源是单次生成（Response）**，不是跨轮次的会话线程。② 提供 `store` 开关，**默认 `true`**：服务端存储该次生成的输入输出条目。③ 提供 `previous_response_id`，由服务端**逆向走链**拼接历史上下文，调用方无需重传全部历史。④ **不持久化完整事件历史**：在途增量事件仅在生成生命周期内于进程内有界缓冲，终态后经保留窗口即释放。⑤ **不提供会话线程级订阅**：流式订阅范围永远是单次生成。⑥ **不做开屏还原**：删除渲染快照（气泡历史 / 运行列表 / 快照序号协议）。⑦ **输出条目由执行端在终态直接提交，不由事件流回放派生**。⑧ 保留期、删除接口、加密与否均为**配置项**，不硬编码合规策略。 |
| **代价** | 服务端持有生成内容，删除权与保留期治理从可选变为必需；新增一层持久化存储与其运维 |
| **SUPERSEDES** | D19 ①③⑦；D18 ①③④⑤⑥⑧⑨ |

### 核心命题：存储 ≠ 订阅

这两件事被长期混为一谈，是本决策要拆开的关键：

| | 存储 | 订阅 |
|---|------|------|
| 目的 | 下一轮**按需**拼接上下文 | 本次生成**实时**推送进度 |
| 读取方式 | 服务端内部读，调用方只给一个标识 | 调用方长连接持续读 |
| 生命周期 | 天级（可配置） | 单次生成时长 + 短保留窗口 |
| 承载 | 持久化、跨节点共享、高可用 | 进程内内存、宿主节点独占 |

存储不蕴含订阅能力：服务持有内容用于拼接，不等于要提供「订阅一个对话线程」的流式接口。反之订阅也不蕴含存储：实时推送完可以立即丢弃。**因此「存内容」与「不做会话级订阅 / 不做开屏」可以同时成立**，这正是本次交付边界。

### 背景澄清（决策溯源）

最初提出的「不存储会话侧业务相关的对话记录」，所指是**业务侧用于辅助渲染的完整事件历史**（含思考过程、工具进度、渲染提示等，需回放才能转为模型上下文），而非生成内容本身。厘清后与 `store: true` 并不冲突：前者不持久化，后者持久化。此段仅记录边界为何落在此处，**不构成术语定义**——规范性文本一律使用 [`spec.md`](../requirements/spec.md) §1.2 的术语。

### ⑦ 为何是架构约束而非实现细节

**自证链条**：在途事件缓冲被定义为有界、瞬态、终态即释放（结论 ④）。若最终输出必须回放事件流才能得出，则事件日志被迫成为持久化真相源——它就必须无界、必须跨节点、必须长期保存，与 ④ 直接冲突，且完整事件历史将不得不持久化，⑤⑥ 一并失守。

故写入路径必须是两条独立通道：

| 通道 | 内容 | 目的地 | 生命周期 |
|------|------|--------|---------|
| `append` 增量事件 | 可含任意仅供渲染的内容 | 在途缓冲 | 瞬态 |
| `complete` 提交规范化输出条目 | 只含协议子集条目 | 上下文库 | 天级 |

**有利副作用**：事件流可自由携带渲染专用内容而完全不污染存储条目——两者本就不经同一路径。这使「事件流表达力」与「存储纯净度」不再互相牵制。

> ⚠️ 未来若有人以「减少一次写入」「让 complete 更轻」为由改为从事件流派生输出，将**无声推翻整个存储边界**。此约束已立为不变量并配 L0 断言，不接受口头承诺。

### 走链的四类断裂必须显式报错

> **此节的「走链」措辞已被 D24 修订**：断裂检查的位置从「读取时回溯」移到「创建时固化快照」，但「显式报错、不静默降级」的结论不变。见 D24 的「断裂检查移到了创建时」表。

| 断裂 | 错误 | 为何不能静默 |
|------|------|------------|
| 某环缺失或已过期 | `ChainBroken` | 静默降级为单轮 ⇒ 模型突然失忆，表现为「AI 忘了上文」的偶发问题，极难归因 |
| 被引用者 `store=false` | `NotStored` | 同上，且掩盖调用方的用法错误 |
| 被引用者属其他租户 | `CrossTenant` | 静默跳过等于默许跨租户探测 |
| 深度或体积超限 | `ChainTooLong` / `ChainTooLarge` | 静默截断 ⇒ 上下文被无声裁掉，输出质量下降且不可复现 |

**统一原则：宁可显式失败，不可静默降级。** 静默截断与静默驱逐一律禁止。

### 否决方案

| 方案 | 否决理由 |
|------|---------|
| 完全无状态（`store:false` 唯一模式，调用方每轮重传全部历史） | 已由需求反转否决。服务端拼接上下文 ⟺ 服务端持有历史，无第三条路 |
| 只存内容指纹（HMAC），不存原文 | 指纹是单向的，**无法参与上下文拼接**，与 `previous_response_id` 不兼容。指纹只能做事后定责，见 D20 ⑧ 与 [`04-content-integrity.md`](../design/04-content-integrity.md) |
| 客户端持密钥、服务端存密文托管 | 服务端拼接上下文时必须解密才能交给模型，密钥必然经服务端，「服务端无法读取」的性质不成立，只是把复杂度换成了幻觉 |
| 全量物化每一环（每个生成存完整历史，读取 O(1)） | ~~存储量随链长平方增长；且同一段历史在每环重复存储，删除单环无法真正删除内容，与删除权要求冲突。~~ **此否决已被 D24 推翻**：删除语义定为「从对话移除」后，该理由不再成立，全量物化成为唯一能兼顾「删除后对话继续」与「删除精确」的方案 |
| 保留开屏快照以支持「打开历史对话」 | 该能力属渲染层，需完整事件历史支撑，与 ④ 冲突。历史对话由调用方持有的 transcript 渲染；服务端 `GET` 只返回最终生成对象 |

## D21 可靠性分层：三类存储的差异化投入

| | |
|---|---|
| **需求** | 高可靠、高可用、灾备诉求；`parameters.md` §5.2 可用性 99.9% |
| **结论** | ① **上下文库与账本**：真实持久化、**同城多可用区主备 + 定期备份**、**同库同事务**。② **在途事件缓冲**：保持**进程内内存**，配**四项缓解**（优雅停机 / 启动期孤儿收口 / 部分用量入账 / 上下文库不可用时拒写）。③ 不做跨地域灾备。④ 上下文库不可用时**拒绝写入**（503），绝不降级为静默不存。⑤ 三层高可用为**条件触发**的后续入口，触发条件与选型预案见下。 |
| **代价** | 网关进程非计划崩溃时，其宿主的在途生成失败需重试（历史完好）；月损失率量化见 `parameters.md` |
| **RESTATES** | D11——分承载结论不变，理由更新为「高频在途缓冲 vs 低频上下文库」 |

### 分层依据

| 存储 | 丢失后果 | 写频率 | 高可用价值 | 高可用成本 | 本期决策 |
|------|---------|--------|-----------|-----------|---------|
| 上下文库 | **历史永久丢失，调用方无法继续对话** | ~70/s | **最高** | 低（常规库主备） | 真库 + 多可用区 + 备份 |
| 账本 | 生成记录 / 计费 / 幂等键丢失 | ~70/s | **高** | 低（与上同库） | 同库同事务 |
| 在途事件缓冲 | 调用方重试该次生成 | **~2 万/s** | 中 | **最高** | 进程内内存 + 四项缓解 |

这正是 D11 的当代表述：两条路径写频率相差约三个数量级，必须分承载。**结论未变，只是路径的名字变了。**

### 关于在途高可用的诚实结论

不回避：共享中间件（Redis Streams / 消息队列）**确实**能买到真实可用性。但价值仅集中于两种情形：

| 崩溃对象 | 进程内内存 | 共享中间件 | 差异是否真实 |
|---------|-----------|-----------|------------|
| **网关挂、执行端存活** | append 失败，该生成被孤立作废 | 执行端改投他节点，**生成不中断** | ✅ **真实收益** |
| 执行端挂 | 新 attempt 重跑 | 新 attempt 重跑 | ❌ 无差异 |
| 整机 / 可用区故障 | 重跑 | 重跑 | ❌ 无差异 |
| **滚动发布** | 在途全丢 | 无损 | ✅ **真实收益** |

第 2、3 行无差异的根因：**LLM 生成本身不可中途续跑**（模型 API 性质，非架构缺陷）。按 attempt 栅栏语义（INV-5/6），重试必然是新 attempt，旧 attempt 的部分输出必须作废，否则输出交织违反 CR-3。故即使事件一条不丢，调用方读到的也只是「失败前的部分输出 + 失败事件」，生成不会继续。

而两处真实收益的处置不同：

- **滚动发布**（最高频事件）：由**优雅停机零成本消除**——发布是计划内动作，可先拒新、等在途自然完成再退出。这不需要任何中间件。
- **非计划网关崩溃**：无法消除。按 `parameters.md` 量化，月损失率约 **0.031%**（悲观 0.093%），满足 99.9% 但**几乎无余量**。

> 结论：进程内内存不是"凑合"，而是在**优雅停机已消除高频损失**的前提下的成本最优选择。但余量很薄，四项缓解**不是可选项**。

### 四项缓解（缺一不可）

| # | 缓解 | 消除的问题 |
|---|------|-----------|
| 1 | **优雅停机**：拒新 → 等在途归零或超时 → 退出 | 滚动发布造成的在途全损（最高频） |
| 2 | **启动期孤儿收口**：按节点标签将账本中归属本节点的未终态记录置失败 | 心跳超时 90s 的长时间挂起 → 秒级明确失败 |
| 3 | **部分用量入账**：中途作废时记录该 attempt 已消耗的 token | 计费对不上账 |
| 4 | **上下文库不可用时拒写**：返回 503 | 链在后续轮次无声断裂（最隐蔽的失败） |

### 三层高可用的升级触发条件

满足任一即重开本决策（新增 `SUPERSEDED BY`）：

| # | 触发条件 | 判定方式 |
|---|---------|---------|
| 1 | 非计划网关崩溃导致的失败率 **> 0.05%/月** | 实测，不接受预判 |
| 2 | 单次生成时长 **P99 > 15 分钟** | 优雅停机不再可行（drain 窗口过长） |
| 3 | 合作方明确要求「网关故障对生成无感知」并接受延迟与成本 | 产品需求提出即触发 |

**届时选 Redis Streams，而非消息队列**（以下结论已从早期选型草稿提取进本正文，草稿随即归档，不再被引用）：

| 维度 | Redis Streams | 消息队列（JetStream / TDMQ 等） |
|------|--------------|------------------------------|
| 游标模型 | **按标识范围随机定位**，与 `starting_after=N` 同构 | 消费者游标模型，需额外维护「序号 ↔ 队列位点」映射 |
| 高基数短命 topic | 一个键即一条流，创建销毁廉价 | 每次生成一个 topic ⇒ **元数据抖动** |
| 追加延迟 | 内存写，亚毫秒 | 三副本持久化，**毫秒级** ⇒ 影响逐字输出体感 |
| 生命周期匹配 | 分钟级短流，`MAXLEN` 天然有界 | 面向长期保留设计，短流是反模式 |

**该决定可逆**：`ResponseEventLog` 端口形状即抽象层，升级只需新增适配器，领域层与接入层零改动（D14）。

### 两条转发路径性质完全不同

多节点部署下有两处「非本节点」的数据访问，**必须分开描述**，否则临时措施会被当成正式设计固化：

| 路径 | 访问对象 | 性质 | 直连是否可能 |
|------|---------|------|------------|
| `route_inflight` | 在途事件缓冲 | **永久架构特征** | **不可能**——状态在特定进程堆内，无共享端点可连 |
| `route_content` | 上下文库 | **临时措施** | 共享库后**应当直连** |

实现手段是能力标志 `ContextStore::is_shared()`：内存实现返回 `false`（走定向转发），SQL 实现返回 `true`（直连）。**接真库时接入层零改动**，且**链亲和路由自动失效**——否则长会话会把流量钉死单节点，制造热点。

流式请求只能**代理**不能 307 重定向：重定向暴露内部拓扑，且跨区或经负载均衡后调用方未必能直达宿主节点。

### 否决方案

| 方案 | 否决理由 |
|------|---------|
| 三层存储全上共享中间件 | 在途层成本最高、收益最低（见诚实结论表）；且引入毫秒级追加延迟损害逐字输出 |
| 在途缓冲也留内存但**不做**四项缓解 | 余量仅 0.031%→0.093%，无缓解则滚动发布单项即可击穿 99.9% |
| 上下文库不可用时降级为「不存但继续生成」 | 本次生成看似成功，下一轮走链断裂。**故障被推迟到无关的后续请求**，是最难排查的失败模式 |
| 跨地域灾备 | 复杂度与 99.9% 目标不匹配（继承 D8）；同城多可用区已满足 |
| 返回 307 让客户端直连宿主节点 | 暴露拓扑；跨区 / LB 后未必可达；对公开 API 不可接受 |

## D22 协议封闭子集与严格拒绝

| | |
|---|---|
| **需求** | 对外提供「类 OpenAI Responses」标准服务；覆盖面最广而非 1:1 全集 |
| **结论** | ① 对外协议为官方 Responses 的**封闭子集**，范围见 [`06-protocol-subset.md`](../design/06-protocol-subset.md)。② **严格拒绝未知字段与未知类型**（400），不静默忽略、不兜底透传。③ 类型层用**封闭枚举 + `deny_unknown_fields`**，不使用 `flatten` 保留未知字段。④ 以 `openai/openai-openapi` 的 `openapi.yaml` 为权威事实来源，**只提取 Responses 相关 schema 子集**，并锁定所依据版本。⑤ 子集范围是**可发布契约**，随服务一并交付。⑥ 立**链闭合性**约束：输出条目类型集合 ⊆ 可接受的输入条目类型集合。⑦ 部署规则：**网关先行升级**。 |
| **代价** | 调用方按官方全集调用会大面积 400，必须发布子集规范；扩展子集需一次显式变更 |
| **SUPERSEDES** | D19 ③ 的门面定义（`POST /v1/sessions` 等会话端点） |

### 严格拒绝没有取舍

一般认为「严进」是在兼容性上让步换安全性。**此处不成立**——因为严格拒绝未知参数**恰好也是官方行为**（官方对未识别参数返回 400）。故：

| | 宽进（忽略未知） | 严进（拒绝未知） |
|---|---|---|
| 安全性 | 差（未知字段可能是攻击面或语义变更） | **好** |
| 与官方行为一致性 | **差**（官方会 400，我们放过） | **好** |
| 调用方排障 | 差（参数写错了却静默生效默认值） | **好**（立即报错并指明字段） |

三项全胜，无需权衡。

### 封闭子集使四个 serde 陷阱由构造消失

早期曾考虑「接受未知类型 + `#[serde(flatten)]` 保留未知字段」以求往返不丢字段。该路线的四个陷阱在封闭子集下全部消解：

| 原陷阱 | 封闭子集下 |
|--------|-----------|
| 未知条目类型解析失败 | **变成期望行为**——本就要返回 400 |
| `untagged` 兜底掩盖真实的字段级错误 | **不需要兜底**；用内部标签封闭枚举，错误如实上报并指明字段 |
| 逐层 `flatten` 漏层丢字段 | **不需要 `flatten`** |
| `flatten` 与数值精度冲突（整数经 `f64` 失真） | `flatten` 消失；且用量字段类型化为 `u64`，不经过 `f64`——比原方案更彻底 |

同时官方那三个「必须原样回传」的字段（消息阶段标记、加密推理内容、程序指纹）**全部失效**：它们由执行端产生，而执行端是本系统自有组件，子集不含这些特性即不存在这些字段。

### 严进的风险转移必须显式处理

风险性质从「静默损坏」转为「显式拒绝」——方向正确，但需三条配套：

| # | 风险 | 处置 |
|---|------|------|
| 1 | **链闭合性**：存储的输出条目会在下一轮作为输入回放。若执行端产出了输入校验器不接受的类型，**自家链就断了** | 立为不变量：输出类型 ⊆ 输入可接受类型，配 L0 断言 `assert_output_items_are_valid_input` |
| 2 | **部署顺序**：执行端先升级并产出新类型 ⇒ 网关拒绝 ⇒ 线上 400 突增 | 规则：**网关先行升级**（先放宽接受面，再升执行端），写入部署文档 |
| 3 | **调用方大面积 400** | 发布自有协议子集规范，从加分项升为**必要交付物** |

> 第 1 项最易被忽略：它是**自伤型**风险，不需要外部调用方参与就能触发。

### 只提取子集，不全量生成

`openapi.yaml` 覆盖 Chat Completions / Assistants / Fine-tuning / Batch / Audio 等全产品线，全量生成会引入数万行无关类型。做法：

1. 提取 Responses 相关 schema 子集，据以手写类型（保留对不变量的编码能力，如封闭枚举拒绝条目引用）
2. **锁定并记录所依据的规范版本**，作为对外「兼容到哪一版」声明的依据
3. CI 定期拉取上游做字段级 diff 并告警

> ⚠️ 第 3 项的性质是**「是否扩展子集」的产品决策输入，不是正确性门禁**——上游新增字段不代表本服务有缺陷，故该检查**不阻塞**构建。混淆这一点会导致上游每次发版都堵住流水线，最终被禁用。

### 拒绝清单中两项的额外理由

| 拒绝项 | 除「不在子集内」之外的理由 |
|--------|--------------------------|
| **条目引用**（`item_reference`） | 它允许按标识引用任意历史条目，**可绕过走链的逐环租户校验**——是一条越权读取路径。即使将来扩展子集也须先解决归属校验 |
| **内联二进制**（base64 图片 / 文件） | 请求体体积失控，且使上下文链的字节上限失效。仅接受文件标识或 https 链接引用；链接需过内网地址段拦截（SSRF 纵深防御） |

### 否决方案

| 方案 | 否决理由 |
|------|---------|
| 1:1 实现官方全集 | 含推理项、程序执行、计算机操作、托管工具等大量与本服务无关的特性；实现与验证成本远超收益 |
| 宽进 + `flatten` 保留未知字段 | 四个 serde 陷阱（见上）；且与官方 400 行为不一致 |
| 由 `openapi.yaml` 全量代码生成 | 数万行无关类型；生成代码无法编码本服务不变量（如封闭枚举拒绝条目引用） |
| 自定义协议（不对齐官方） | 放弃「调用方可直接改 base_url 接入」的最大卖点 |
| 上游 diff 作为阻塞门禁 | 上游每次发版都会堵住流水线，必然被禁用，反而失去告警能力 |

## D23 生成由宿主节点内部执行，取消拉取式执行端

| | |
|---|---|
| **需求** | [`spec.md`](../requirements/spec.md) FR-4/5/6 修订版；D21 落地共享账本后暴露的矛盾 |
| **结论** | ① **取消外部拉取协议**：删除 `/v1/agent/claim`、`/heartbeat`、`/append`、`/complete` 四个端点与独立执行端进程。② 生成由**创建它的节点**在进程内取用并执行——生成者与在途缓冲持有者**恒等**。③ 取用限定**本节点作用域**：`claim` 携带 `NodeTag`，账本不得把某节点的生成交给另一节点。④ 保留 attempt 栅栏与回收机制：执行上界到期与节点重启仍须抬高 attempt 并明确失败。⑤ 出站调用经 `CompletionsRequestScheduler` 端口，具体 provider 为适配器。 |
| **代价** | 失去「执行端独立伸缩」与「执行端与接入端异构部署」的可能；节点须同时承载接入与执行负载 |
| **SUPERSEDES** | D18 ②（Worker 按 Turn 领取）；D11 关于「领取路径」的措辞（分承载结论不变，见下） |

### 触发原因：D21 让拉取模型的一个前提失效

拉取模型隐含假设「领取者即宿主」。在 mem 后端下该假设自动成立——每个节点各持自己的账本，只能领到本节点的活。**D21 把账本改为共享后，这个前提消失了**，而领取与追加的代码没有跟上：

| 步骤 | 结果 |
|---|---|
| node-b 创建 | id 为 `resp_node-b_x`，`Created` 事件落入 **node-b** 缓冲 |
| 连着 node-a 的执行端领到它 | 账本共享且**无节点过滤**，领取成功 |
| 执行端追加增量 | 落入 **node-a** 缓冲 |
| 订阅者按 id 路由 | 被送往 **node-b** —— **只见 `Created`，永远收不到增量** |

该缺陷此前无任何测试覆盖：`node-a-sql.toml` / `node-b-sql.toml` 存在但无 runner 引用，L2 跑 mem 后端，`scenarios/l3/` 为空。

### 为何选内部执行而非补齐拉取模型

| 方案 | 否决理由 |
|---|---|
| 领取加节点亲和（保留拉取） | 可修正缺陷，但执行端与节点绑定：某节点积压时，连着其他节点的执行端只能空转。缺陷源头——生成者与缓冲持有者可分离——依然存在，只是被约束住 |
| 追加事件按 `node_tag` 转发到宿主 | 每个 token 多一跳。D11 量化的正是 ~2 万条/s 这一侧，在其上再加一跳与该决策直接冲突 |
| **内部执行（采纳）** | 生成者与缓冲持有者**恒等**，矛盾从构造上消失，无需额外机制维持对齐 |

### 与 D11 / D21 的关系

D11「低频账本与高频在途缓冲必须分承载」**结论不变**：两侧仍相差约三个数量级，仍分承载。本决策只取消了「领取」作为一条**跨进程协议**——账本的取用转换仍在，只是调用方从 HTTP 客户端变为同进程任务。

D21 的三层分工不变。本决策消除的正是 D21 落地时与拉取模型之间的缝隙。

### 保留 attempt 栅栏的理由

内部执行让并发双领在结构上难以发生，但栅栏**不可删除**：

- 执行任务卡死超过执行上界时，清扫器会将其回收；若该任务此后苏醒并追加，其 attempt 已过期，必须被拒（FR-6 / INV-6 / CR-7）
- 本地重试若引入，新旧 attempt 的输出绝不可交织（CR-3）

> ⚠️ 「内部执行后不会双领，故可去掉 attempt」是错误推论：卡死任务的苏醒写入与回收是并发的，与领取无关。此约束已配 L0 断言。

### 并发边界的归属

节点须限制同时进行的执行任务数，否则一批排队生成会一次性打满出站调用。该上限是**节点资源**的属性，配置于执行引擎；而**provider 侧的限流、排队、重试属于 scheduler 适配器**（见 `00-architecture-review.md` §10.2）。二者不可混为一谈：前者保护本进程，后者遵守对端约束。

## D24 上下文物化：每个生成保存完整上下文快照

| | |
|---|---|
| **需求** | 删除中间环节后，对话仍须能继续；删除语义定为「从对话移除」（非合规抹除） |
| **结论** | ① 每个生成**物化**其创建时可见的完整上下文，存为**扁平的条目副本**（`context: Vec<ResponseItem>`），另以 `context_depth` 记录祖先环数（扁平列表无法从条目数反推轮数）。② 读取上下文不再回溯 `previous_response_id`——读快照即可，O(1)。③ 删除是**记录级**的：只删该 response 自身的记录，下游快照里那份继承的副本原样保留，下游环节存活且可继续。④ `previous_response_id` 降为元数据（回显、协议兼容），不再参与读取。⑤ 链的各类断裂检查（缺失、跨租户、未存储、超限）从「读取时回溯发现」移到「**创建时**固化快照的解析」——快照一旦固化即自洽，读取不可能再遇到断裂。 |
| **代价** | 存储 O(n²)（n 为单链轮数）；删除即单行删除，无级联写 |
| **SUPERSEDES** | D20 中否决「全量物化」的一行（否决理由随删除语义变更而不再成立，见下） |

### 为何推翻 D20 的否决

D20 否决全量物化的决定性理由是「删除权无法履行：删一环，其内容仍存在于后续每一环」。这个理由成立的前提是 **DELETE 的语义是合规抹除**——即「删除后内容不得留存」。

本决策把语义明确为**「从对话移除」**：删除后，被删环节的**记录**从对话中消失，但它贡献给后续对话的**内容副本**作为继承的历史保留——那不是「没删干净」，而是「这条内容已经成了后续对话的一部分」。语义一旦如此，D20 的否决理由不再成立，全量物化成为**唯一**能同时满足两个目标的方案：

| 目标 | 链式（旧） | 全量物化（本决策） |
|---|---|---|
| 删除中间环后对话继续 | ❌ 断裂，显式报错 | ✅ 继续（快照自包含） |
| 删除是精确的 | ✅ 彻底移除 | ✅ 记录级：只删记录，副本保留 |

空间 O(n²) 不是本决策的主体代价——n 是单条链的轮数（几十量级），不是总消息数。删除是单行操作，无需级联写，也没有「半删状态」需要原子性来防范。

### 记录级删除，而非内容级抹除

「从对话移除」不等于「从继承它的每个快照里抹除」。后者是合规抹除的语义，与 D24 的前提相悖。

由此快照**不需要来源标记**：既然删除永不追溯剔除，`ContextSegment.source` 就没有用途，快照退化为扁平的 `Vec<ResponseItem>`。`context_depth` 单独存储，因为扁平列表无法从条目数反推轮数（一轮可含多个条目，如工具调用）。

### 快照的完整性边界

`context` 快照是「继承来的历史」，其权威来源是各环节自身的 `input_items`/`output_items`（受 integrity 签名保护）。快照本身不单独签名——它只是副本，篡改快照会影响后续对话的上下文，但不会伪造某个环节的权威内容。此权衡有意为之，代价可接受。

### 断裂检查移到了创建时

| 断裂 | 旧位置（读取时回溯） | 新位置（创建时） |
|---|---|---|
| 环缺失或已过期 | 读取时 `ChainBroken` | 创建时解析 `previous` 即失败 |
| 被引用者 `store=false` | 读取时 `NotStored` | 创建时同上 |
| 被引用者跨租户 | 读取时 `CrossTenant` | 创建时解析 `previous` 校验租户，失败即拒 |
| 深度/字节超限 | 读取时 | 创建时固化快照前检查 |

由此 `CrossTenant` 与「链中环缺失」不再由读取产生；快照一旦固化即自洽，读取 O(1) 且不可能失败于断裂。

## D25 执行进程独立与在途缓冲共享化，能力层抽离

| | |
|---|---|
| **需求** | 执行端独立水平扩容与高可用；接入与执行故障风险分离；接入协议层与 responses 能力解耦 |
| **结论** | ① **执行进程独立**：Agent 拆为独立进程，经 `ResponseLedger` 端口直连共享账本领活，账本不设独立逻辑层服务。② **在途缓冲共享化**：`ResponseEventLog` 从进程内内存升级为共享中间件（具体方案后置：Redis Streams / TDMQ 等），端口形状不变。③ **读写网关不拆**：Gateway 同时承载 write（`POST /v1/responses`）与 read（`GET retrieve/stream`）；调用方不直连共享缓冲。④ **claim 回退为全局作用域**：废除 node-scoped claim，保留 attempt 栅栏与回收。⑤ **能力层抽离**：新增 `nova-responses` 承载 responses 用例编排，`nova-responses-core` 保持零依赖不合并。 |
| **代价** | 引入共享中间件与其追加延迟（D21 已量化）；Agent 从零 IO 变为持有账本连接与凭证；运维面增加一层 |
| **SUPERSEDES** | D23（整体）；D21 的「在途缓冲留进程内内存」条款 |

### 触发原因

D23 的代价表明确写着「失去执行端独立伸缩与异构部署；节点须同时承载接入与执行负载」。这三点现成为真实诉求：执行负载（长生成、模型等待）与接入负载（HTTP、SSE）混合部署互相抢占；接入与执行的故障无法隔离（Agent 崩拖累 Gateway，Gateway 崩中断执行）；执行端无法单独水平扩容。

### 核心问题：缓冲归属，而非 pull 目标

D23 用「内部执行」让生成者与在途缓冲持有者恒等，从而消掉「增量落错进程」。拆进程会重新激活该矛盾，故决策变量是**在途缓冲归属**，而非「Agent 从哪 pull」：

| 方案 | 缓冲位置 | 结论 |
|---|---|---|
| A 缓冲随 Agent | Agent 实例进程 | 需新增 response→agent 实例路由与发现，改动最大 |
| B 缓冲在 Gateway，Agent 回写宿主 | Gateway 节点 | 每 token 多一跳（与 D11 冲突）；Gateway 崩时 append 失败、生成照样作废——进程分离了，故障影响没分离 |
| **C 共享缓冲（采纳）** | 共享中间件（Redis Streams / TDMQ 等） | 缓冲不再属于任何进程，D23 的缺陷从构造上消失；D21 已预留可逆路径（`ResponseEventLog` 端口即抽象层，升级只需新增适配器） |

### Agent 领取：直连账本，不设账本逻辑层

Agent 经 `ResponseLedger` 端口直连共享账本领活（非经 Gateway HTTP）：

- **claim 是低频**：≈ 账本写频率 `~70/s`，与增量 `~2 万/s` 差三个数量级，Agent poll 不构成压力
- **账本不加逻辑层**：claim 在 SQL 后端就是一条原子 UPDATE，状态锁由 DB 的 CAS 提供；语义封装在 sql adapter（库，非服务），Agent 复用
- **Agent 不感知账本实现**：只见 `Arc<dyn ResponseLedger>`（端口），不感知 DB 协议/SQL schema；不直连发 SQL——否则破坏可测性（mem 后端无 DB 单测）、DRY、可替换性

### 不拆读写网关（协议对齐结论）

依据 OpenAI Responses 协议行为：

- `POST /v1/responses` + `stream=true`：SSE 从 POST **同连接**建立，主流用法把写与初始流绑定
- `GET /v1/responses/{id}` + `stream=true` + `starting_after`：独立 SSE 订阅与断点续传；**`starting_after` 为 OpenAI 官方参数**（非本服务自造）
- `GET retrieve`（非 stream）返回**当前状态**对象：未完成返回 `status: in_progress` 的部分对象，**不失败**——这是 `background=true` 轮询机制的语义基石

故 Gateway 同时承载 write 与 read，不拆两个服务；调用方不直连共享中间件（消息中间件不出 SSE，且读路径需租户鉴权）。**故障隔离靠「缓冲共享化 + Agent 独立」，不靠读写分离。**

### 能力层抽离

Gateway 现混杂三层职责（接入协议 / 执行驱动 / 后台维护），根因是 D23 后执行宿主与协议接入合并：

- 新增 `nova-responses` 承载用例编排（create / resolve_chain / 幂等 / 三种投递 / 订阅编排），不含 axum / HeaderMap / 状态码
- `nova-responses-core` **不合并**：零 workspace 依赖是 check-deps 不变量；端口与用例抽象层次不同
- 分两步：先作 gateway 内无 axum 的 service 模块，再视多协议复用独立成 crate

### 连带改写

| 项 | 改动 |
|---|---|
| `spec.md` FR-4 | 「宿主节点内部执行」→ 执行端独立进程经端口领活 |
| `spec.md` FR-30 / 术语「宿主节点」 | 在途按 node_tag 定向路由 → 共享缓冲后任意节点直读 |
| L0 `claim-locality` 用例 | 废除（node-scoped claim 不再成立） |
| `check-deps` 门禁 | 「claim 必须节点作用域」→ 全局 claim + 栅栏 |
| `ResponseEventLog` | 新增共享适配器（端口不变，方案后置） |

### 否决方案

| 方案 | 否决理由 |
|---|---|
| 同机 sidecar（缓冲仍在 Gateway） | 仅进程隔离；Gateway 崩仍中断执行；「同机绑定」仍属架构约束而非纯部署 |
| 领取加节点亲和（保留拉取 + 缓冲在 Gateway） | 执行端与节点绑定，积压时空转（D23 已否决） |
| 追加事件按 node_tag 转发回宿主 | 每 token 多一跳，与 D11 冲突（D23 已否决） |
| 读写网关拆为两个服务 | 违背主流 stream=true 同连接形态；故障隔离不需要它 |
| 合并 core 与 service | 破坏 core 零依赖不变量与端口/用例分层 |

## D26 自研会话层：状态如何广播

> ⛔ SUPERSEDED BY [D28](#d28-会话能力下沉数据层conversation-吸收-session)

| | |
|---|---|
| **需求** | 多端同步、并发互斥、业务事件（`spec.md` FR-42~45） |
| **结论** | ① session 只管**状态如何广播**：一条持久信封事件流 + 一把单轮次锁 + 业务事件。② 会话层**绝不持有内容**——信封只放引用（response id、终态、业务载荷），对话条目的唯一真相源仍是响应链物化快照（D24）。③ **取锁与其宣告事件原子**：`begin_turn`/`end_turn` 是单次端口调用，锁状态与 `TurnStarted`/`TurnCompleted` 在同一事务/临界区落地，不存在「已锁无事件」或「有事件无锁」的中间态。④ 会话流与 token 流是**两条流**：前者低频持久（每轮 2~3 信封，触顶拒绝追加不驱逐），后者高频瞬态（D20 ④，可驱逐）。⑤ 绑定互斥：一个容器至多一个会话。 |
| **代价** | 新增一个持久存储端口与一个自研 API 面；终态路径必须逐个打通释放锁，漏一条即会话永久锁死 |

### 为何 session 必须存在，而不是并进 conversation

conversation（D27）回答「上下文从哪来」，是官方协议；session 回答「状态怎么广播」，是官方协议没有的东西。若把锁与事件流塞进 conversation，官方 SDK 会看到一堆它不认识的字段；若反过来只做官方 conversation，多端同步就没有任何承载。两者各一件事，各自正交。

### 取锁与事件为何必须同一端口

拆成「锁 CAS + 事件 append」两个端口调用看似更「正交」，实则错误：崩溃落在两次调用之间，会留下「已锁但流上无事件」或「宣告了轮次却没锁」——各端界面与服务端永久分歧，且外部无法修复。原子性是存储的属性，所以配对的落点必须是存储端口。

### 会话流为何持久且拒绝驱逐

| | token 流（D20 ④） | 会话信封流（本决策） |
|---|---|---|
| 频率 | ~2 万条/s | 每轮 2~3 条 |
| 丢一条 | 订阅者少一段回放 | 丢掉某轮发生过这件事的唯一记录 |
| 处置 | 有界 + 可驱逐（INV-40） | 有界 + **拒绝追加**（INV-59） |

二者相差三个数量级，这正是 D20 ④「不持久化完整事件历史」在会话层依然成立的原因——会话流不是那个「完整事件历史」。

### 残留锁的处置

锁可能比持有者活得久（进程死在账本终态迁移与释放锁之间，或释放调用本身失败）。处置不是超时（误杀长轮次）也不是永久 409，而是**以「持有者是否已终态」为准绳**：账本知道确切答案，`Busy { holder }` 把持有者告诉调用方，调用方据账本判定后条件释放并重试一次。条件释放不发事件——终态事件已由完成方发过。

### 否决方案

| 方案 | 否决理由 |
|---|---|
| session 并入 conversation | 官方 SDK 见未知字段；锁与广播是两个问题 |
| 锁与事件分两端口 | 崩溃落在两调用之间，产生外部不可修复的分歧态 |
| 会话流驱逐旧事件 | 丢掉「某轮发生过」的唯一记录 |
| 超时释放残留锁 | 误杀长轮次（与 SR-2 冲突）或把卡死留给用户 |
| 自研发起轮次端点 | 与标准 `POST /v1/responses { conversation }` 是同一件事的第二种写法，必然分叉 |

## D27 会话容器退化为链尾指针

> ⛔ SUPERSEDED BY [D28](#d28-会话能力下沉数据层conversation-吸收-session)

| | |
|---|---|
| **需求** | 官方 conversation 兼容（`spec.md` FR-40/41） |
| **结论** | ① conversation 只存 `{ id, tenant, last_response_id, metadata }`，**不存任何条目**。② `POST /v1/responses { conversation }` 把它解析为链尾 `ResponseId`，再走既有 `resolve_chain`（D24 零改动）——conversation 不是第二种上下文来源，只是第二种指定锚点的方式。③ 终态时 `advance(conv, resp)` 更新指针，**后写胜出**（无 CAS），且只推进**提交了输出**的轮次。④ 官方 `items` 子资源不实现：容器无条目可增删，读历史走 session 的 transcript。⑤ 只实现官方 4 个 CRUD 端点。 |
| **代价** | 裸用 conversation（无 session）时并发轮次无锁，指针后写胜出（与官方一致） |

### 为何能退化成指针

官方语义是「conversation 中的 items 会被前置到 input 之前」。而 `resolve_chain(last_response_id)` 返回的正是「该链全部祖先 items + 它自身 items」——从调用方视角**完全等价**。既然已有完整的链装配，conversation 只需记住「链尾在哪」，无需第二份条目。

由此消掉的东西比预期更多：

| 原方案的东西 | 退化后 |
|---|---|
| `ContextSource` 两来源归一 | 不需要——conversation 转成 `previous_response_id`，只有一条上下文路径 |
| `conversation_items` 表 + 复合索引 | 不需要 |
| `snapshot_items` 热路径 + N+1 约束 | 不需要 |
| `ConversationItemId` | 不需要 |
| 官方 items 分页/排序/`include`/删除语义 | 一次性消失 |
| D24 「零改动」 | 从「靠归一保证」变成**结构上不可能改动** |

### 为何 advance 是后写胜出而非 CAS

CAS 的失败方需要一个冲突码，而官方协议没有这个码——裸用 conversation 的官方 SDK 会收到一个它不认识的 409。接受后写胜出与「官方也未保证并发轮次顺序」一致。会话锁（`max_in_flight=1`）已经在需要的地方防住了并发。

### 与 D24 的关系

conversation 退化为指针后，`resolve_chain` 仍是上下文装配的唯一入口。这是**结构性保证**而非约定：不存在第二份条目，就没有第二条读取路径可以分叉。

### 否决方案

| 方案 | 否决理由 |
|---|---|
| conversation 存条目 | 同一段对话两份副本，必然分叉，且与 D24 物化快照重复 |
| 实现官方 `items` 子资源 | 容器无条目可增删；分页/排序/`include`/删除语义全在此，成本高、收益零 |
| advance 加 CAS | 官方 SDK 收到不存在的 409 |
| 只有 conversation 没有 session | 多端同步无承载；且官方无会话概念 |

## D28 会话能力下沉数据层：conversation 吸收 session

| | |
|---|---|
| **需求** | 消除 `responses ↔ session` 的概念纠缠；让生命周期同步不绑定在 responses 实现上（`spec.md` FR-42~45） |
| **结论** | ① conversation 退化为**单实体**：链尾 `last_response_id` + 在途互斥 `active_response_id` + 事件流（`turn_started`/`turn_completed`/`business`/`response_deleted`），`Session`/`SessionId`/`SessionStore`/`SessionsService` 全部移除。② **互斥（锁）下沉到 conversation 数据层**：`active_response_id` 的 CAS（空 → 占用，忙 → 409）；responses / engine / cancel / sweep 只通过 conversation 锚定生命周期，**不感知 session 的存在**。③ 端点统一 `/v1/conversations`：官方 CRUD 对象纯净（不暴露 `last`/`active`），自研能力走子资源（`GET /` 列表、`/{id}/events`、`/{id}/transcript`、`POST /{id}/events`）。④ **去写前探活**：失败即感知 + 补偿回撤，仅保留启动探活。 |
| **代价** | 跨 core / nova-responses / agent / 三个 adapter / sweep 的大重构；conversation 语义扩展（自研子资源）；删除 conversation 即删除会话对象（历史内容仍留在响应记录，D24 物化快照） |

### 为何互斥下沉 conversation，而非注入 hook

注入式 lifecycle hook 是「运行时埋点」：依赖注入只解决了**编译期**解耦（responses 不 import session 类型），却把同步能力绑死在「我们的 responses 实现里埋了调用点」上。换成任何第三方 / 官方 responses 实现，那里没有埋点，session 就失去取锁 / 释放锁能力。

互斥下沉到 conversation 后，同步的锚点变成**协议 / 数据层本来就存在的东西**：任何 responses 实现创建 response 都会带 `conversation`（官方字段），都会经过 `ConversationStore`。`active_response_id` 的 CAS 在存储层原子完成，第三方实现只要遵守 conversation 字段，互斥就自动成立，不依赖实现埋点。

### 取锁与事件为何仍须同一端口（延续 D26 ③）

下沉不改变原子性约束：`acquire_active`（CAS 占用）+ 发 `turn_started` 必须同一事务 / 临界区落地，`release_active` + 发 `turn_completed` 同理。差别只在端口从 `SessionStore` 移到 `ConversationStore`，原子性仍是存储的属性。

### 为何去写前探活

写前 `health()` 每次写操作多一次 RPC（延迟 + 压力），而它防的是「库明确不可用」这一低概率事件。低概率失败用「治疗」（失败即返回错误 + 补偿回撤）而非「预防」（每次都探活）更划算。启动探活保留：一次 fail-fast，成本可忽略，避免服务空转 503。

### 否决方案

| 方案 | 否决理由 |
|---|---|
| 注入式 lifecycle hook | 运行时埋点，换 responses 实现丢同步能力 |
| session 独立保留（D26 原案） | `find_by_conversation` 反查 + `responses → session → response` 概念纠缠 |
| 写前探活 | 延迟 + 压力，低概率失败不值得预防 |
| 自研能力塞进官方 conversation 对象 | 官方 SDK 见未知字段（`active_response_id` 等），污染协议 |

## D29 Agent 结构解耦：编排器 + AgentRunner + 模拟验证进程

| | |
|---|---|
| **需求** | 把「进程壳 / 任务编排 / Agent 执行（React 循环）」三层解耦；completions 出站抽象不再是主结构 |
| **结论** | ① **编排器 `AgentRuntime`**（crate `nova-agent` → `nova-agent-runtime`）只负责 claim → 组装 `AgentTask` → 调 `AgentRunner` → 提交结果（complete / fail），**不含 React 循环**。② **`AgentRunner` trait** 承载执行抽象（定义在 nova-agent-runtime），React 循环落在实现里；增量事件经 `AgentEventSink` 回传，`Stop` 传导 fence 移动；编排器与 runner 之间以强类型 `AgentTask` / `AgentOutcome` / `AgentEventSink` 契约约束，字段全部用 core 的稳定类型。③ **completions 出站抽象下沉**：`CompletionsRequestScheduler` / `CompletionsSink` / `ToolExecutor` 及 `CompletionsRequest` / `CompletionsOutcome` 等类型从 core 移除，`StoredResponse.tools` 改存 inbound 形状（单一数据源，provider 转换由 runner 内部做）；这些并入 `testing/agentd-mock`，不再是主结构端口。④ **模拟验证进程 `nova-agentd-mock`** 移到 `testing/` 下，装配 mem-server 客户端 + `MockAgentRunner`（React 循环：completions-mock/http + calculator）+ `AgentRuntime`；`new` / `start` 分离以支持缩扩容。⑤ **取消正确性与及时性分离**：fence（`attempt`）保证正确性（拒绝过期写入），sink `Stop` 单一传导取消及时性；heartbeat 仅保活，不承担取消通知。⑥ 生产 agentd 另行建设，对接真实 agent SDK（Moray）+ redis/mq，本期只预留 `AgentRunner` 抽象。 |
| **代价** | core 移除 completions 模块与两个端口；`completions-mock` / `completions-http` / `tool-calculator` 三 adapter 并入 agentd-mock；测试迁移 |

### 为何编排与执行分离，而非继续内嵌

编排器关心「何时 claim、如何组装、结果落到哪」，执行关心「如何跑完一次 React 循环」。把后者留在编排器里，换 provider / 换 agent SDK 都要改编排器；抽成 `AgentRunner` 后，编排器只见一个 trait，mock provider 与真实 agent SDK 落在同一接缝两侧。

### 为何 completions 出站抽象下沉，而非留在 core

completions 出站（`CompletionsRequest` / `CompletionsRequestScheduler` 等）是「如何调模型 provider」的实现细节，生产 agent 走真实 SDK（Moray）用不到。留在 core 会让主结构（存储 / 领域 / 协议契约）背负一个只服务验证的 provider 抽象。下沉到 `testing/agentd-mock` 后，core 只保留存储 / 领域 / 协议契约，抽象与否由具体 `AgentRunner` 实现自决。

### 取消正确性与及时性分离

fence（`attempt`）保证**正确性**——过期 attempt 的写入被拒绝。但 fence 无法让一段正在进行的模型调用停下（期间无 append，感知不到取消）。及时性由 sink `Stop` 单一承担：流式场景（tokens/sec 100~200）下每个 token 都 append，几 ms 内传导取消并让 scheduler 停止模型调用；heartbeat 是低频保活，不承担取消通知通道。模型 / tool 的「无输出等待期」取消靠 `exec_deadline` 超时 + 输出开始后的 `Stop` + reap 兜底。

## D30 存储分工重构：responses 走事件流，conversation 存持久快照

| | |
|---|---|
| **需求** | 会话是长期对话的权威来源；responses 有明确 TTL，不适合做长期还原的数据源；存储选型不归领域层管，只提供 trait 接口与接入文档 |
| **结论** | ① **移除 `ContextStore` 端口**，职责拆分：快照读写并入 `ConversationStore`，response 对象检索重建并入 `ResponseEventLog`（回放流）。② **responses 由事件流承载（短期 TTL）**：账本 `ResponseRecord` 只存元数据（`response_id`/`tenant_id`/`previous_response_id`/`conversation_id`/`input_items`/`tools`/`model`/`instructions`/`store`/状态/用量/时间戳），**不再物化祖先快照**；`GET /v1/responses/{id}` 在 TTL 内由事件流回放重建，TTL 后 404。③ **conversation 存持久物化主快照**：新增 `read_snapshot`（agent 取上下文 / transcript 渲染）与 `append_turn`（终态把本轮 input+output 追加进快照）；存储从 D24 的 O(n²) 降为 O(n)。④ **创建只记元数据**：新轮不再物化快照，只解析锚点并校验链上限（fail-fast 保留）；执行时 agent 按锚点读一次主快照重建 LLM 上下文。⑤ **终态数据源禁止回放**：`append_turn` 的条目来自编排层 `AgentOutcome.items` 直接提交，**绝不从事件流回放派生**（INV-48 RESTATE）。⑥ **原子性边界迁移**：INV-34 从「创建时 ledger+context 同事务」改写为「终态时 `ledger.complete` + `conversation.append_turn` 同事务」。⑦ **裸链（`previous_response_id` 无会话）**：沿账本反查归属会话读快照；无会话归属的裸链从事件流重建其 input+output（TTL 内），更深裸链按 `ChainBroken` 显式失败。⑧ **delete 为记录级**：删账本记录 + 事件流，会话快照副本保留（沿用 D24 语义），广播 `ResponseDeleted`。⑨ **存储选型不做**：只交付领域层 trait + mock 参考实现 + 接入要求文档（`07-storage-integration.md`），外部接入方自行实现 `ResponseLedger`/`ConversationStore`/`ResponseEventLog` 并注入。 |
| **代价** | 会话快照单调增长（需冷存储保留策略）；裸链恢复受事件流 TTL 约束；`store=false` 无持久载体；L1 场景（harness + YAML）需随语义重设计 |
| **SUPERSEDES** | D24 的「每生成物化完整快照（O(n²)）」条款；D28 的「conversation 不存条目」条款 |
| **RESTATES** | INV-48（输出非回放派生，断言改为「销毁流后会话快照完整」）；INV-34（原子性边界迁到终态） |

### 为何由 conversation 承担长期内容，而非 responses

responses 有 `expires_at_ms` TTL，会被清扫；把「长期对话还原」寄生其上，还原窗口就等于 responses 的保留期——这正是上游用 conversation 存 items（不受 30 天限制）而 responses 只有 30 天 TTL 的分工。D30 对齐这一分工：conversation 是 system of record，responses 是短期执行记录。

### 为何移除 ContextStore 而非保留改名

D28 已论证 conversation 不合并快照的理由（锁/事件流的写事务形状不同）。但该理由成立的前提是「快照在 responses 上」。D30 把快照移回 conversation 后，ContextStore 与 ConversationStore 的边界重叠——快照读写归会话、检索重建归事件流，中间不再需要独立的「内容库」端口，故整端口移除，职责拆分。

### 为何原子性边界从创建时迁到终态

D24 下创建时要 `ledger.create` + `context.put` 同事务（INV-34），因为创建即物化快照。D30 下创建只写元数据，无需双写；真正的持久内容在终态提交（`ledger.complete` + `conversation.append_turn`），故原子性约束迁到这里。

### 为何禁止回放派生（INV-48 保留）

事件流是有界瞬态，随时可被驱逐；若 `append_turn` 从流回放派生，持久历史就依赖一个可驱逐缓存。数据源必须是编排层手中的 `AgentOutcome.items`——L0 `output-provenance` 断言「销毁事件流后会话快照仍完整」。

## D31 ledger 端口拆分：发起/领取分离，准入整体移除

| | |
|---|---|
| **需求** | 下游宿主（nova / tuvvi）已有自己的分布式任务系统；聚合端口 `ResponseLedger`（12 方法 + `AdmissionControl` supertrait）迫使每个后端实现整套语义，且两侧消费者（gateway 能力层 / 执行编排）互相背包袱。决策讨论在 nova 主仓（`nova/docs/plans/nova-chat-ledger-port-split`），实施在 nova-chat |
| **结论** | ① **拆分 trait**：`ResponseLedger` 删除，拆为 `ResponseIntake`（发起侧：create / cancel / delete / delete_by_tenant / get）与 `ResponseClaimSource`（领取侧：claim / heartbeat / complete / reap / record_partial_usage / check_attempt / get）；`get` 两侧各一份，实现方以固有 helper 收敛读逻辑。② **准入整体移除**（对原决策文档 §3.2 的修订，不引入 `AdmissionGate`）：`AdmissionControl` 端口删除，`CreateOutcome` 收缩为 `Accepted / Duplicate`，`in_flight` 移出契约——过载拒绝与降级属任务管控，由宿主进程在调用端口之前自决，不在 responses 机制内。③ **持有者改型**：`ResponsesDeps { ledger: Intake, claims: ClaimSource }`（sweeper 的 reap 走领取侧）、`AgentRuntimeDeps.ledger: ClaimSource`、gateway `AppState.ledger: Intake`。④ **同后端装配两次**：从具体 `Arc<T>` 分别 coerce 到两个 dyn，不依赖 trait upcasting。⑤ **drain 改固定宽限**：优雅停机不再轮询 `in_flight`（在途计数属任务管控），改为服务满 `drain_timeout` 宽限窗口后退出；越窗残余由下一节点 sweep 收口（INV-45 不变）。 |
| **代价** | FR-33 / CR-8 / INV-29 / INV-30 / INV-32 从需求与覆盖基线划除（移交业务侧）；五个准入 verify 场景与 `overload-integrity` conformance 用例删除；下游（nova `MongoResponseLedger`、tuvvi `PgResponseLedger`）需自行拆 impl |
| **SUPERSEDES** | 无（`ResponseLedger` 无独立 ADR；其拆分推翻的是端口聚合本身） |
| **RESTATES** | D25 的「执行经端口直连」条款（端口名改为 `ResponseClaimSource`）；INV-45 / INV-51 / INV-5/6 / FR-3 / D25 断言原样保留 |

### 为何准入彻底移除而非外移为 gateway 装饰器（AdmissionGate）

原决策文档 §3.2 保留 `CreateOutcome::ReadOnly/Overloaded` 并把它产生的地方移到 gateway 装配层。实施时修订为整体移除：标准 Responses 协议中没有准入判定语义（429/503 是传输层运维行为，不是协议领域语义），read_only/pending_limit/in_flight 本质是宿主的任务管控能力——无论判定发生在后端还是 gateway 装饰器，`in_flight()` 都强制每个后端实现按状态聚合扫描的查询语义。移除后 `ResponseIntake` 回归纯记录簿，语义边界与标准协议对齐。

### 为何 sweep 不随之迁移

reap 的「失联判定」确属任务管控，可由宿主领取侧实现自含；但善后（Failed 终态事件、轮次归档 D30、锁释放 D28）是 responses 领域生命周期，宿主任务系统做不了。拆分后 sweeper 已只依赖 `ResponseClaimSource`——注入缝已打开（宿主 reconciler 在后端层回收时，本地 reap 空转无害），契约级迁移待下游联调时再评估。
